## Словарик

Краткий справочник аббревиатур и базовых понятий.

| Термин | Расшифровка | Cмысл |
|---|---|---|
| **DPDK** | Data Plane Development Kit | Фреймворк Intel для быстрой обработки пакетов в сетевых приложениях |
| **NIC** | Network Interface Card | Сетевая карта — физическое устройство приёма/передачи пакетов |
| **[EAL](#eal-environment-abstraction-layer)** | Environment Abstraction Layer | Базовый слой DPDK: инициализация hugepages, ядер CPU, драйверов |
| **[PCI](#pcipcie-и-dma-как-пакет-попадает-в-ram)** | Peripheral Component Interconnect | Шина для подключения устройств (NIC, GPU и др.) к материнской плате |
| **[RX](#rx-queue-receive-queue)** | Receive | Приём пакетов (входящий трафик) |
| **[TX](#tx-queue-transmit-queue)** | Transmit | Передача пакетов (исходящий трафик) |
| **[mbuf](#rte_mbuf)** | Memory Buffer | Структура DPDK для хранения одного пакета в памяти |
| **[mempool](#rte_mempool)** | Memory Pool | Заранее выделенный набор буферов (mbuf) фиксированного размера |
| **[NUMA](#numa-non-uniform-memory-access)** | Non-Uniform Memory Access | Архитектура, где у каждого CPU есть "своя" быстрая память |
| **MAC** | Media Access Control | Уникальный аппаратный адрес сетевой карты (6 байт, напр. `08:00:27:95:BD:AE`) |
| **[VFIO](#vfio-pci)** | Virtual Function I/O | Механизм ядра Linux для прямого доступа к PCI-устройству из userspace |
| **[lcore](#lcore-в-dpdk)** | Logical Core | Логическое ядро CPU, к которому DPDK привязывает поток |
| **[Burst](#rte_eth_rx_burst)** | — | Пачка пакетов, обрабатываемых за один вызов (16/32/64 штуки) |
| **Kernel Bypass** | — | Обход ядра ОС — пакеты идут напрямую NIC → userspace без syscall |
| **[Polling](#polling-опрос)** | — | Активный опрос NIC в цикле вместо ожидания прерывания |
| **[CPU socket](#cpu-сокет-cpu-socket)** | — | Физический процессор (чип) на плате; в сервере может быть 1–2+ сокета |
| **[DMA](#pcipcie-и-dma-как-пакет-попадает-в-ram)** | Direct Memory Access | NIC пишет/читает данные напрямую в/из RAM без копирования через CPU |
| **[Hugepages](#страницы-памяти-tlb-и-hugepages)** | — | Большие страницы памяти (2MB/1GB), уменьшают нагрузку на TLB |
| **[TLB](#страницы-памяти-tlb-и-hugepages)** | Translation Lookaside Buffer | Кэш переводов виртуальных адресов в физические; TLB miss = лишняя задержка |
| **[Atomic](#atomic-атомарность)** | — | Атомарная операция: выполняется целиком, без “разрыва” другими потоками |
| **[Checksum](#checksum-что-это-и-где-используется)** | — | Контрольная сумма: защита заголовков/датаграмм от ошибок |
| **[Endianness](#endianness-host-и-network-byte-order)** | — | Порядок байт; сетевые заголовки хранятся в big-endian (network order) |
| **[EtherType](#ethertype)** | — | Поле Ethernet, которое говорит, какой протокол внутри (например IPv4) |
| **[IPv4](#rte_ipv4_hdr-ipv4-header)** | Internet Protocol v4 | Сетевой протокол L3; в примере формируем IPv4 заголовок вручную |
| **[UDP](#rte_udp_hdr-udp-header)** | User Datagram Protocol | Транспортный протокол L4; в примере формируем UDP заголовок вручную |


## Архитектура железа для DPDK

### CPU: физические и логические ядра

- **Физическое ядро** — физический блок, который находится внутри центрального процессора (CPU) и выполняет вычисления, обрабатывает команды и управляет потоками данных.
- **Логическое ядро (logical CPU)** — то, что видит ОС (CPU0, CPU1, ...). При SMT/Hyper-Threading одно физическое ядро обычно даёт 2 логических.

Важно: логические ядра одного физического делят многие ресурсы (часть конвейеров, кэши, порты исполнения), поэтому 2 логических не даст 2× производительность.

### SMT / Hyper-Threading

SMT работает так: в одном физическом ядре продублировано «архитектурное состояние» (регистры, счётчики, контекст), и ОС может планировать два потока так, будто это два отдельных процессора. 

Что остаётся общим (упрощённо):

```
Физическое ядро
├── Thread A (logical CPU X): регистры/контекст
├── Thread B (logical CPU Y): регистры/контекст
└── Общие ресурсы: execution units, L1/L2 (частично), доступ к L3/памяти
```

### Кэш CPU (L1/L2/L3) и latency

Кэш — это быстрая память рядом с ядром CPU, которая хранит недавно использованные данные.

```
RAM  (медленно)
 ↑
L3   (общий)
 ↑
L2   (на ядро)
 ↑
L1   (на ядро, самый быстрый)
```

Если поток мигрирует на другое ядро, «тёплый» кэш остаётся на старом ядре → на новом возникают cache miss (когда нужных данных нет в кэше и приходится идти в более медленную память) и скачки задержки.

### Affinity (привязка потока к ядру)

**Thread affinity** — запрет миграции потока между CPU-ядрами. DPDK делает это через EAL: ты явно задаёшь, на каких CPU запускать потоки, чтобы latency (задержка от прихода пакета до того, как ты смог его обработать) была стабильной.

### lcore в DPDK

Логическое ядро CPU, к которому DPDK привязывает поток исполнения.  
Привязка к конкретному ядру устраняет накладные расходы на переключение контекста и миграцию между ядрами.
DPDK использует термин **lcore** как «DPDK-ядро исполнения» (EAL thread), которому назначается `lcore_id`.


- Узнать текущий lcore: 

```cpp
unsigned id = rte_lcore_id();
```

- Перебрать активные lcore:

```cpp
uint16_t i = 0;
RTE_LCORE_FOREACH(i) {
    // i = lcore_id
}
```

### Как работает параметр --lcores

`--lcores` задаёт **маппинг**: какие lcore создать и к каким CPU (logical CPU ОС) их привязать. Формат: `<lcores[@cpus]>[,<lcores[@cpus]>...]`

Примеры из документации:

- `--lcores=1-3` — запустить потоки на CPU 1,2,3 с теми же lcore id. 

Для образовательных целей удобно думать так:

- `--lcores=0,1` → два потока DPDK: main на lcore 0 и worker на lcore 1 (как в примере 03).

### CPU-сокет (CPU socket)

**CPU-сокет** — это физический процессор как отдельный чип на материнской плате.
В сервере может быть 1 сокет (single-socket) или 2/4+ сокета (multi-socket).

Почему это важно для DPDK:
- У каждого сокета своя локальная память (RAM) и свои пути к устройствам (PCIe).
- Если поток крутится на сокете A, а память/устройство на сокете B, появляются лишние задержки.

### NUMA (Non-Uniform Memory Access) и сокеты

В NUMA-системах память «разделена по сокетам»: у каждого CPU-сокета есть своя локальная RAM.
Доступ к локальной памяти быстрее, а к памяти другого сокета — медленнее (и часто менее предсказуем).

Мини-схема:

```
Socket 0 (NUMA node 0)                Socket 1 (NUMA node 1)
+-----------------------+             +-----------------------+
| CPU cores + L3 cache  |             | CPU cores + L3 cache  |
| Memory controller     |             | Memory controller     |
| Local RAM             |             | Local RAM             |
+-----------------------+             +-----------------------+
            ^                                       ^
            |                                       |
            +--------     interconnect      --------+
                 remote memory = медленнее
```

Практика для DPDK (короткое правило):
- lcore (где крутится polling) + NIC + mempool должны быть на одном NUMA node.

Подсказки из кода DPDK:
- `rte_eth_dev_socket_id(port)` даёт NUMA node, где «сидит» NIC.
- `rte_socket_id()` даёт NUMA node текущего lcore.
- Если `rte_eth_dev_socket_id()` вернул -1 (неизвестно), используют `rte_socket_id()` как fallback.

### Каналы памяти (memory channels) и параметр -n

**Канал памяти** — физический «канал» между контроллером памяти CPU и планками RAM; больше каналов = выше пропускная способность памяти.

EAL-аргумент `-n <NUM>` задаёт число каналов памяти (исторически использовалось для модели распределения памяти/hugepages). В учебных примерах часто ставят `-n 2` или `-n 4`. 

### Страницы памяти, TLB и hugepages

ОС работает со страницами памяти (pages): чаще всего 4KB.
**TLB (Translation Lookaside Buffer)** — маленький, но очень быстрый кэш в CPU, который хранит соответствия «виртуальная страница → физическая страница».

Когда приложению нужно много разных страниц (например, большие mempool/ring/таблицы), TLB может не помещать все переводы — возникает **TLB miss** и CPU тратит время на обход таблиц страниц.

**Hugepages** (2MB или 1GB) уменьшают число страниц: меньше страниц → меньше переводов → ниже давление на TLB.
DPDK обычно использует hugepages для памяти под mbuf/mempool, чтобы сделать доступ к пакетным буферам стабильнее.

### PCI/PCIe и DMA: как пакет попадает в RAM

NIC подключена по PCIe и умеет делать **DMA** (Direct Memory Access): писать данные пакета напрямую в заранее подготовленные буферы в RAM (mbuf), без копирования через стек ядра. Это одна из причин низкой задержки в DPDK.

## Архитектура и инициализация
> Новые термины из примера `01-reading-a-packet-from-nic`

### EAL (Environment Abstraction Layer)
Уровень абстракции окружения — фундаментальный слой DPDK, который инициализирует всё необходимое для работы:  
выделяет [hugepages](#hugepages-большие-страницы-памяти), настраивает привязку потоков к ядрам CPU, инициализирует драйверы устройств.  
**Всегда вызывается первым** в любом DPDK-приложении.

```cpp
int32_t return_val = rte_eal_init(argc, argv);
if (return_val < 0) {
    std::cerr << "Unable to initialize DPDK EAL. Error: " << rte_errno << std::endl;
    exit(1);
}
```

**EAL-аргументы командной строки** передаются через `argc/argv` и разделяются от пользовательских аргументов символом `--`:
```
./app --lcores=0 -n 4 -- -s 1 -t 2
         ^EAL args^       ^user args^
```
- `--lcores=0` — использовать ядро CPU №0 для главного потока
- `-n 4` — использовать 4 канала памяти

📎 Документация: https://doc.dpdk.org/guides/linux_gsg/linux_eal_parameters.html

Про аргументы подробнее читать [здесь](#аргументы-rte_eal_init-eal-parameters)

---

### rte_eal_init()
Функция инициализации EAL. Возвращает **количество обработанных EAL-аргументов**.  
После вызова нужно скорректировать `argc` и `argv`, чтобы они указывали на пользовательские аргументы:

```cpp
// До вызова: argc=9, argv = ["./app", "--lcores=0", "-n", "4", "--", "-s", "1", "-t", "2"]
int32_t return_val = rte_eal_init(argc, argv); // вернёт 4
argc -= return_val; // argc = 5  ("--", "-s", "1", "-t", "2")
argv += return_val; // argv теперь указывает на "--"
```

---

### rte_eal_cleanup()
Освобождает все ресурсы, выделенные EAL. Должна вызываться перед завершением программы.

```cpp
rte_eal_cleanup();
return 0;
```

---

### rte_errno
Глобальная переменная DPDK для хранения кода последней ошибки (аналог стандартного `errno`).  
Используется для диагностики при неудачной инициализации EAL и других операциях.

```cpp
if (return_val < 0) {
    std::cerr << "Error code: " << rte_errno << std::endl;
}
```

## Порты и очереди

### Port (Ethernet Port)
В терминологии DPDK **порт** — это сетевой интерфейс (NIC),  
привязанный к DPDK-драйверу (например, `vfio-pci`). Идентифицируется числовым `port_id`.

```cpp
uint16_t port_ids[RTE_MAX_ETHPORTS] = {0};
int16_t total_port_count = 0;

RTE_ETH_FOREACH_DEV(id) {
    port_ids[total_port_count] = id;
    total_port_count++;
}
```

---

### RTE_ETH_FOREACH_DEV
Макрос для итерации по всем доступным Ethernet-портам в системе.

```cpp
int16_t id = 0;
RTE_ETH_FOREACH_DEV(id) {
    // id принимает значения 0, 1, 2, ... для каждого найденного порта
}
```

---

### RTE_MAX_ETHPORTS
Константа — максимально допустимое число Ethernet-портов в одном DPDK-приложении.  
Используется для ограничения размера массива `port_ids`.

---

### RX Queue (Receive Queue)
Очередь приёма пакетов на уровне NIC. Каждый порт может иметь несколько RX-очередей  
(Multi-Queue), что позволяет параллельно обрабатывать пакеты на разных CPU-ядрах.  
В этом примере используется одна RX-очередь.

```cpp
const uint16_t rx_queues = 1;
const uint16_t tx_queues = 0; // TX не нужен — только читаем
```

---

### TX Queue (Transmit Queue)
Очередь передачи пакетов. В примере `01-reading-a-packet-from-nic` не используется (`tx_queues = 0`),  
так как задача только в чтении пакетов.

---

### rte_eth_dev_configure()
Конфигурирует Ethernet-порт: задаёт число RX/TX очередей и режим их работы.

```cpp
rte_eth_conf portConf = {
    .rxmode = { .mq_mode = RTE_ETH_MQ_RX_NONE }, // одна очередь, без балансировки
    .txmode = { .mq_mode = RTE_ETH_MQ_TX_NONE }
};

return_val = rte_eth_dev_configure(port_ids[0], rx_queues, tx_queues, &portConf);
```

---

### RTE_ETH_MQ_RX_NONE
Режим одиночной очереди приёма — пакеты не распределяются между несколькими очередями.  
Альтернативы: `RTE_ETH_MQ_RX_RSS` (распределение по хэшу), `RTE_ETH_MQ_RX_DCB` и др.

---

### rte_eth_rx_queue_setup()
Настраивает конкретную RX-очередь порта: задаёт глубину очереди (число дескрипторов)  
и привязывает её к memory pool для хранения принятых пакетов.

```cpp
return_val = rte_eth_rx_queue_setup(
    port_ids[0],   // port_id
    i,             // queue_id (0, 1, 2, ...)
    256,           // nb_desc: глубина очереди (число дескрипторов)
    portSocketId,  // socket_id: NUMA-узел
    nullptr,       // rx_conf: NULL = использовать дефолтную конфигурацию
    memory_pool    // mb_pool: пул памяти для пакетов
);
```

---

### rte_eth_promiscuous_enable()
Включает **promiscuous mode** (неразборчивый режим) на порту.  
В этом режиме NIC принимает **все** пакеты в сети, не только адресованные её MAC-адресу.  
Полезно для мониторинга трафика и сниффинга.

```cpp
return_val = rte_eth_promiscuous_enable(port_ids[0]);
// Не все драйверы поддерживают — ошибку можно игнорировать
```

---

### rte_eth_dev_start()
Запускает Ethernet-порт после его конфигурации. После вызова порт начинает принимать пакеты.

```cpp
return_val = rte_eth_dev_start(port_ids[0]);
```

---

### rte_eth_dev_socket_id()
Возвращает NUMA socket ID, к которому физически подключена сетевая карта.  
Важно для оптимизации: memory pool желательно создавать на том же NUMA-узле, что и NIC,  
чтобы избежать медленного cross-socket доступа к памяти.

```cpp
const int16_t portSocketId = rte_eth_dev_socket_id(port_ids[0]);
const int16_t coreSocketId = rte_socket_id(); // NUMA-узел текущего ядра CPU
// Используем тот, что >= 0 (валидный)
int16_t socketId = (portSocketId >= 0) ? portSocketId : coreSocketId;
```

## Управление памятью

### Hugepages (Большие страницы памяти)

См. также: [Страницы памяти, TLB и hugepages](#страницы-памяти-tlb-и-hugepages).
Стандартная страница памяти Linux — 4KB. DPDK использует страницы по **2MB или 1GB**,  
что резко снижает количество промахов TLB и ускоряет доступ к большим буферам пакетов.

Настройка (из Задания №2):
```bash
echo 1024 | sudo tee /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages
# Выделяем 1024 hugepages по 2MB = 2GB под DPDK
```

---

### rte_mempool
Структура пула памяти DPDK — заранее выделенный набор буферов фиксированного размера.  
Используется для хранения принятых пакетов (объектов `rte_mbuf`).  
Пул создаётся один раз и переиспользуется, избегая динамического `malloc`/`free`.

```cpp
rte_mempool *memory_pool = rte_pktmbuf_pool_create(
    "mempool_1",             // имя пула (уникальное)
    1023,                    // число буферов в пуле
    512,                     // cache_size: кэш на lcore для скорости аллокации
    0,                       // priv_size: приватные данные на mbuf (не нужны)
    RTE_MBUF_DEFAULT_BUF_SIZE, // размер одного буфера = 2048 + 128 байт
    rte_socket_id()          // NUMA-узел
);
```

> Число буферов `1023` не просто так. Для оптимальной работы mempool рекомендуется  
> использовать значения вида `2^n - 1` (степень двойки минус один).

---

### rte_mbuf
Структура, описывающая один сетевой пакет в DPDK. Содержит метаданные пакета  
и указатель на буфер с сырыми данными.

Ключевые поля:
| Поле | Тип | Описание |
|---|---|---|
| `data_len` | `uint16_t` | Длина данных в этом сегменте |
| `pkt_len` | `uint32_t` | Общая длина пакета (все сегменты) |
| `nb_segs` | `uint8_t` | Число сегментов (обычно 1) |
| `port` | `uint16_t` | ID порта, с которого пришёл пакет |
| `buf_addr` | `void*` | Указатель на буфер данных |

```cpp
rte_mbuf *received_packets[32];
// После rte_eth_rx_burst() каждый элемент массива — указатель на принятый пакет
std::cout << "Packet length: " << received_packets[i]->data_len << std::endl;
```

---

### RTE_MBUF_DEFAULT_BUF_SIZE
Константа = **2176 байт** (2048 + 128). Стандартный размер буфера для одного пакета:
- `2048` байт — данные пакета (достаточно для стандартного Ethernet MTU = 1500 байт)
- `128` байт — заголовок `rte_mbuf` и служебные данные

---

### rte_pktmbuf_free_bulk()
Освобождает массив `rte_mbuf` обратно в memory pool за один вызов.  
Важно освобождать пакеты после обработки, иначе пул закончится.

```cpp
rte_pktmbuf_free_bulk(received_packets, rx_packets);
```

---

## Приём пакетов

### rte_eth_rx_burst()
Ключевая функция для получения пакетов — **вытаскивает пачку (burst) пакетов**  
из RX-очереди NIC в массив `rte_mbuf`. Возвращает фактическое число принятых пакетов.

```cpp
rte_mbuf *received_packets[32]; // буфер под 32 пакета
uint16_t rx_packets = rte_eth_rx_burst(
    port_ids[0],       // port_id
    0,                 // queue_id
    received_packets,  // массив для записи указателей на пакеты
    32                 // максимум пакетов за один вызов
);
```

> **Burst-обработка** — вместо обработки пакетов по одному   берём сразу пачку (16, 32, 64...). Это амортизирует накладные расходы на вызов функции  и улучшает использование кэша CPU.

---

### Polling (Опрос)
Вместо прерываний (interrupt-driven I/O) DPDK использует **активный опрос** NIC в цикле.  
Поток непрерывно вызывает `rte_eth_rx_burst()`, проверяя наличие новых пакетов.  
Это устраняет задержку от обработки прерываний (~microseconds).

```cpp
while (!exit_indicator) {
    rx_packets = rte_eth_rx_burst(port_ids[0], 0, received_packets, 32);

    if (rx_packets == 0) {
        std::this_thread::sleep_for(10us); // небольшая пауза при отсутствии пакетов
        continue;
    }
    // обработка пакетов...
}
```

> `sleep_for(10us)` показан для примера.

---


## Отправка пакетов
> Новые термины из примера `02-sending-a-packet-from-nic`

### Режим “только TX”
В этом примере мы не принимаем пакеты, а только отправляем. Поэтому порт конфигурируется так:

```cpp
const uint16_t rx_queues = 0;
const uint16_t tx_queues = 1;
```

Идея: мы создаём `rte_mbuf`, вручную записываем в него байты Ethernet/IP/UDP пакета и отдаём драйверу на отправку.

---

### rte_mempool_get()
Получает **один** буфер (`rte_mbuf`) из `mempool`. В отличие от `rte_pktmbuf_alloc()`, здесь мы берём объект напрямую из пула.

```cpp
rte_mbuf *packet = nullptr;
if (rte_mempool_get(memory_pool, reinterpret_cast<void **>(&packet)) != 0) {
    std::cout << "Error: Unable to get memory buffer from memory pool" << std::endl;
}
```

Важно:
- Если пул пуст, это чаще всего значит, что где-то забыли освобождать mbuf (утечка), либо скорость генерации/отправки выше, чем скорость “возврата” буферов.

---

### rte_pktmbuf_mtod()
Возвращает указатель на начало области данных (data area) в mbuf.

```cpp
uint8_t *data = rte_pktmbuf_mtod(packet, uint8_t *);
```

Дальше `data` используется как обычный указатель на байты, в которые мы пишем заголовки и payload.

---

### rte_eth_tx_burst()
Ключевой API для отправки: кладёт указатели на `rte_mbuf` в TX-очередь.

```cpp
const uint16_t tx_packets = rte_eth_tx_burst(port_ids[0], 0, &packet, 1);
```

Что важно понимать:
- Это “burst” API: можно отправлять пачку mbuf за один вызов, но в примере отправляют 1.
- Возвращаемое число — **сколько реально принято драйвером в TX-очередь**.
- Если `tx_packets == 0`, значит пакет не ушёл (очередь перегружена или нет ресурсов) → mbuf нужно освободить самому.

---

### Освобождение mbuf при ошибке передачи
В примере есть важный паттерн:

```cpp
if (tx_packets == 0) {
    rte_pktmbuf_free(packet);
}
```

Почему так:
- Пока пакет не принят драйвером, ответственность за `rte_mbuf` остаётся на приложении.
- Если забыть `rte_pktmbuf_free()`, mempool постепенно опустеет.

---

## Как работает Burst

### RX Burst (приём)

```
NIC Hardware (физическая карта)
┌─────────────────────────────────────────────┐
│  RX Ring (дескрипторы)                       │
│  ┌────┬────┬────┬────┬────┬────┬────┬────┐  │
│  │ p0 │ p1 │ p2 │ p3 │ p4 │ p5 │ p6 │ p7 │  │
│  └──┬─┴──┬─┴──┬─┴──┬─┴────┴────┴────┴────┘  │
└─────┼────┼────┼────┼──────────────────────────┘
      │    │    │    │
      ▼    ▼    ▼    ▼       rte_eth_rx_burst(port, queue, pkts[], 32)
┌─────────────────────────────────────────────┐
│  pkts[]  — массив указателей на rte_mbuf    │
│  ┌───────┬───────┬───────┬───────┐          │
│  │ *mbuf │ *mbuf │ *mbuf │ *mbuf │          │
│  └───┬───┴───┬───┴───┬───┴───┬───┘          │
│      │       │       │       │  return: 4   │
└──────┼───────┼───────┼───────┼──────────────┘
       │       │       │       │
       ▼       ▼       ▼       ▼
┌──────────────────────────────────────────────┐
│          mempool (hugepages)                  │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐        │
│  │mbuf 0│ │mbuf 1│ │mbuf 2│ │mbuf 3│        │
│  │[data]│ │[data]│ │[data]│ │[data]│        │
│  └──────┘ └──────┘ └──────┘ └──────┘        │
└──────────────────────────────────────────────┘
```

### TX Burst (отправка)

```
Приложение собирает пакеты в массив pkts[]
┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
│mbuf 0│ │mbuf 1│ │mbuf 2│ │mbuf 3│
│[pkt] │ │[pkt] │ │[pkt] │ │[pkt] │
└──┬───┘ └──┬───┘ └──┬───┘ └──┬───┘
   │        │        │        │
   ▼        ▼        ▼        ▼
rte_eth_tx_burst(port, queue, pkts[], 4)
             │
     ┌───────▼──────────────────────┐
     │   TX Ring (NIC descriptor)   │
     │ ┌────┬────┬────┬────┐        │
     │ │ p0 │ p1 │ p2 │ p3 │ ...   │
     │ └────┴────┴────┴────┘        │
     └──────────────────────────────┘
             │
     ┌───────▼──────────────────────┐
     │   NIC отправляет в сеть  🌐  │
     └──────────────────────────────┘

  return = 4  → все пакеты приняты драйвером ✅
  return = 2  → 2 не ушли → rte_pktmbuf_free() ⚠️
```

### Почему Burst быстрее, чем по одному?

```
Без burst (по одному):
─────────────────────────────────────────────────────
[overhead][pkt1][overhead][pkt2][overhead][pkt3]...
   ↑ каждый раз: вызов функции, lock, memory access

С burst (пачкой 32):
─────────────────────────────────────────────────────
[overhead][pkt1][pkt2][pkt3]...[pkt32]
   ↑ один overhead на 32 пакета → стоимость на пакет в 32x ниже

Накладные расходы:
- вызов функции (инструкции)
- доступ к дескрипторам NIC
- TLB/cache-line промахи

→ Amortization: чем больше пакетов в burst, тем дешевле каждый.
```


## Сетевые заголовки (Network Headers)
> Термины из примера `02-sending-a-packet-from-nic`: мы формируем Ethernet + IPv4 + UDP вручную.

### Компоновка пакета в памяти
Пакет записывается в `data` последовательно:

```
[data]
  ├─ Ethernet header (rte_ether_hdr)
  ├─ IPv4 header    (rte_ipv4_hdr)
  ├─ UDP header     (rte_udp_hdr)
  └─ Payload (данные)
```

Удобный шаблон указателей:

```cpp
auto *eth = reinterpret_cast<rte_ether_hdr *>(data);
auto *ip  = reinterpret_cast<rte_ipv4_hdr  *>(data + sizeof(rte_ether_hdr));
auto *udp = reinterpret_cast<rte_udp_hdr   *>(data + sizeof(rte_ether_hdr) + sizeof(rte_ipv4_hdr));
uint8_t *payload = data + sizeof(rte_ether_hdr) + sizeof(rte_ipv4_hdr) + sizeof(rte_udp_hdr);
```

---

### rte_ether_hdr (Ethernet header)
Ethernet-заголовок содержит:
- `src_addr` — MAC отправителя,
- `dst_addr` — MAC получателя,
- `ether_type` — какой протокол находится “внутри” (например IPv4).

В примере:

```cpp
rte_ether_hdr *eth_hdr = reinterpret_cast<rte_ether_hdr *>(data);
eth_hdr->ether_type = rte_cpu_to_be_16(RTE_ETHER_TYPE_IPV4);
```

---

### EtherType
**EtherType** — поле в Ethernet-заголовке, которое определяет тип полезной нагрузки.
Например, IPv4 обозначается `RTE_ETHER_TYPE_IPV4`.

---

### rte_ipv4_hdr (IPv4 header)
IPv4-заголовок начинается сразу после Ethernet.
В примере выставляются ключевые поля:
- `version = 4` — IPv4,
- `ihl = 5` — длина IPv4 заголовка 20 байт,
- `time_to_live = 64`,
- `next_proto_id = 17` — UDP,
- `src_addr` / `dst_addr` — адреса источника/назначения,
- `total_length` — длина IP-пакета (заголовок IP + UDP + payload).

---

### rte_udp_hdr (UDP header)
UDP-заголовок идёт после IPv4:
- `src_port`, `dst_port`
- `dgram_len` — длина UDP-датаграммы (UDP header + payload)
- `dgram_cksum` — checksum UDP (в примере = 0)

---

### Endianness: host и network byte order
Сетевые заголовки используют **network byte order** (big-endian).
На x86 host order обычно little-endian, поэтому числа надо конвертировать перед записью в заголовок:

```cpp
udp_hdr->dst_port = rte_cpu_to_be_16(5000);
ipv4_hdr->total_length = rte_cpu_to_be_16(200);
```

---

### Checksum (что это и где используется)
Checksum — контрольная сумма, которая позволяет обнаружить повреждение данных.
В примере:
- IPv4 checksum считается функцией `rte_ipv4_cksum()`.
- UDP checksum оставляют 0 (упрощение для учебного примера).

---

### rte_ipv4_cksum()
Считает checksum IPv4 заголовка. Типичный паттерн:

```cpp
ipv4_hdr->hdr_checksum = 0;
ipv4_hdr->hdr_checksum = rte_ipv4_cksum(ipv4_hdr);
```

---

### Payload (данные приложения)
Payload — это байты после заголовков. В примере его заполняют `memset()` и затем кладут строку.

Важно после сборки пакета правильно выставить длины в mbuf:

```cpp
packet->data_len = packet->pkt_len =
    sizeof(rte_ether_hdr) + sizeof(rte_ipv4_hdr) + sizeof(rte_udp_hdr) + payload_len;
```

## Обработка

> Новые термины из примера `03-reading-and-processing-packets-on-two-logical-cores`.
> Здесь два lcore работают параллельно, обмениваясь пакетами через **ring buffer**.

---

### Идея примера: зачем два потока?

В примере `01` один поток читал пакеты и тут же их обрабатывал.
Проблема: пока поток «думает» над обработкой, новые пакеты могут уже приходить в NIC, и мы их теряем (RX ring переполняется).

**Решение — разделить задачи:**

```
┌─────────────────────────────────────────────────────────────────┐
│   lcore 0 (main thread)        lcore 1 (worker thread)          │
│                                                                  │
│   ТОЛЬКО читает с NIC    ─────▶ ТОЛЬКО обрабатывает пакеты      │
│   как можно быстрее             (считает, парсит, логирует, ...) │
└─────────────────────────────────────────────────────────────────┘
```

Канал передачи между ними — **ring buffer** (кольцевой буфер).

---

### Общая схема работы

```
                       ИНИЦИАЛИЗАЦИЯ (main, lcore 0)
                       ┌────────────────────────────────────┐
                       │ rte_eal_init()                      │
                       │ mempool создан                      │
                       │ NIC настроен и запущен              │
                       │ ring buffer создан                  │
                       └────────────────┬───────────────────┘
                                        │
               ┌────────────────────────▼────────────────────────┐
               │  rte_eal_remote_launch(process_packets, lcore 1) │
               │  → запускает worker асинхронно, не блокирует     │
               └────────────────────────┬────────────────────────┘
                                        │
          ┌─────────────────────────────▼────────────────────────────────┐
          │                    Параллельная работа                       │
          │                                                              │
          │  lcore 0 (PRODUCER)          lcore 1 (CONSUMER)             │
          │  ───────────────────         ─────────────────────────       │
          │  loop:                       loop:                           │
          │    rte_eth_rx_burst()          rte_ring_dequeue_burst()      │
          │    ↓                           ↓                             │
          │    rte_ring_enqueue()          обработка пакета              │
          │    ↓                           ↓                             │
          │    [ring buffer] ──────────▶  rte_pktmbuf_free()            │
          └──────────────────────────────────────────────────────────────┘
                                        │
               ┌────────────────────────▼────────────────────────┐
               │  Ctrl+C → exit_indicator = 1                     │
               │  оба цикла выходят                               │
               │  rte_eal_wait_lcore(lcore 1)                     │
               │  rte_eal_cleanup()                               │
               └──────────────────────────────────────────────────┘
```

---

### Что такое Ring Buffer (кольцевой буфер)

Ring buffer — это **очередь фиксированного размера**, замкнутая в кольцо.
Один конец — для записи (enqueue), другой — для чтения (dequeue).

```
      ┌──────────────────────────────────────────────────────┐
      │             Ring Buffer (размер 1024 - 1)            │
      │                                                      │
      │   head ──▶ [ *mbuf | *mbuf | *mbuf |  ...  | пусто ]│
      │                                        ◀── tail      │
      │                                                      │
      │  lcore 0 кладёт сюда указатели  ─────▶  enqueue()   │
      │  lcore 1 забирает отсюда        ◀─────  dequeue()   │
      └──────────────────────────────────────────────────────┘
```

Важно понимать: передаётся не сам пакет, а **указатель на rte_mbuf** (8 байт).
Сами данные пакета лежат в mempool и не копируются:

```
mempool (hugepages):
┌────────┐ ┌────────┐ ┌────────┐
│ mbuf_0 │ │ mbuf_1 │ │ mbuf_2 │
│ [data] │ │ [data] │ │ [data] │
└───┬────┘ └───┬────┘ └───┬────┘
    │          │          │
    ▼          ▼          ▼
ring: [ &mbuf_0 | &mbuf_1 | &mbuf_2 | ... ]
                     │
       lcore 1: dequeue(&mbuf_1) → работает с mbuf_1 напрямую
```

---

### rte_ring_create()

Создаёт кольцевой буфер.

```cpp
ring_buffer = rte_ring_create(
    "ring_buffer_1",         // уникальное имя
    1024,                    // размер (реальная вместимость = 1024 - 1)
    rte_socket_id(),         // NUMA node
    RING_F_SP_ENQ |          // Single Producer: только 1 поток пишет
    RING_F_SC_DEQ            // Single Consumer: только 1 поток читает
);
```

Почему `1024 - 1`? Ring buffer внутри реализован так, что одна ячейка всегда пустая (чтобы различать «буфер полный» и «буфер пустой»). Реальная вместимость = `size - 1`.

---

### RING_F_SP_ENQ / RING_F_SC_DEQ (SPSC режим)

```
RING_F_SP_ENQ — Single Producer ENQueue
    → запись делает ровно 1 поток → не нужна атомарность
RING_F_SC_DEQ — Single Consumer DEQueue
    → чтение делает ровно 1 поток → не нужны атомарность
```
| Режим | Флаги | Потоков-писателей | Потоков-читателей | Скорость |
|---|---|---|---|---|
| SPSC | `SP_ENQ + SC_DEQ` | 1 | 1 | 🚀 максимальная |
| MPSC | `MP_ENQ + SC_DEQ` | много | 1 | чуть медленнее |
| SPMC | `SP_ENQ + MC_DEQ` | 1 | много | чуть медленнее |
| MPMC | `MP_ENQ + MC_DEQ` | много | много | 🐢 медленнее всего |

---

### rte_ring_enqueue()

Кладёт **один** указатель на mbuf в ring buffer (lcore 0 — producer).

```cpp
for (uint16_t i = 0; i < rx_count; ++i) {
    if (rte_ring_enqueue(ring_buffer, rx_packets[i]) != 0) {
        // Ring переполнен → пакет теряем, освобождаем сами
        rte_pktmbuf_free(rx_packets[i]);
    }
}
```

---

### rte_ring_dequeue_burst()

Забирает пачку указателей из ring buffer (lcore 1 — consumer).

```cpp
rte_mbuf *rx_packets;[2]
uint8_t rx_count = rte_ring_dequeue_burst(
    ring_buffer,
    reinterpret_cast<void **>(rx_packets),
    32,      // макс. штук за раз
    nullptr  // сколько осталось в ring (нам не нужно)
);
if (!rx_count) continue; // ring пустой — ждём
```

---

### rte_eal_remote_launch()

Запускает функцию на **другом lcore** асинхронно — не блокирует вызывающий поток.

```cpp
rte_eal_remote_launch(process_packets, nullptr, logical_cores);[3]
```

```
main (lcore 0)                    lcore 1
──────────────────                ──────────────────────────
remote_launch()   ──────────────▶ [EAL thread просыпается]
    │ (не блокирует)               process_packets(nullptr)
    ▼                                   │
read_packets_from_interface()      while (!exit_indicator)
    │                                   │
    └──── оба крутятся параллельно ─────┘
```

Функция-воркер обязана иметь сигнатуру `int function(void *arg)`.

---

### rte_eal_wait_lcore()

Ждёт, пока lcore завершит функцию, запущенную через `remote_launch`.

```cpp
rte_eal_wait_lcore(logicalCores[1]);
rte_eal_cleanup(); // ← только после этого безопасно
```

```
БЕЗ wait_lcore():              С wait_lcore():
─────────────────              ──────────────────────────────
lcore 0 выходит                lcore 0 ждёт lcore 1
rte_eal_cleanup()              lcore 1 завершается
[lcore 1 ещё работает] → 💥    rte_eal_cleanup()  ← ✅ OK
```

---

### Схема жизни mbuf в примере 03

```
NIC получает пакет
      │
      ▼ 
mempool → mbuf выделен
      │
      ▼ rte_eth_rx_burst()        [lcore 0]
rx_packets[i] = &mbuf
      │
      ▼ rte_ring_enqueue()        [lcore 0]
ring: [ &mbuf | ... ]
      │
      ▼ rte_ring_dequeue_burst()  [lcore 1]
rx_packets[i] = &mbuf
      │
      ▼ обработка пакета          [lcore 1]
      │
      ▼ rte_pktmbuf_free()        [lcore 1]
mbuf возвращается в mempool
```

Между потоками mbuf **не копируется ни разу**. Передаётся только указатель (8 байт).

## Системные концепции

### vfio-pci
Модуль ядра Linux для прямого доступа к PCI-устройствам из пространства пользователя (**kernel bypass**). DPDK использует его для управления NIC без участия ОС-драйвера,  
что исключает накладные расходы на системные вызовы.

```bash
sudo modprobe vfio-pci
sudo ./dpdk-devbind.py -b vfio-pci 0000:00:1f.6
```

---

### dpdk-devbind.py
Утилита DPDK для привязки/отвязки сетевых устройств от драйверов.

```bash
./dpdk-devbind.py --status          # показать все устройства и их текущие драйверы
./dpdk-devbind.py -b vfio-pci 0000:00:1f.6   # привязать устройство к DPDK-драйверу
./dpdk-devbind.py -b e1000 0000:00:1f.6      # вернуть обратно к ОС-драйверу
```

---


### Atomic (атомарность)

**Атомарная операция** — это такая операция над данными, которая выглядит для других потоков как неделимая: либо она ещё не началась, либо уже полностью завершена.

Зачем это нужно:
- Чтобы несколько потоков могли безопасно менять общие счётчики/флаги без мьютексов.
- Чтобы строить lock-free структуры (например, кольцевые буферы), где нет блокировок.

Важно не путать:
- `volatile` **не делает** операции атомарными и не даёт межпоточной синхронизации.
- `std::atomic<T>` (C++) или атомики в DPDK дают атомарность и (при нужном memory order) упорядочивание.

---

### Signals (сигналы ОС)

**Сигнал** — это асинхронное уведомление процессу от ОС (или другого процесса/терминала).
Сигналы полезны, чтобы корректно завершать бесконечные polling‑циклы.

Частые сигналы:
- `SIGINT` — прерывание с терминала (обычно Ctrl+C).
- `SIGTERM` — “попросить завершиться” (например, `kill <pid>` без `-9`).
- `SIGKILL` — “убить сразу” (его нельзя перехватить обработчиком).


---

### terminate() (обработчик сигнала)

`terminate()` в примере — это функция, которую ОС вызывает, когда процесс получил `SIGINT` или `SIGTERM`.
Её задача — **быстро** выставить флаг остановки и выйти.

```cpp
static volatile sig_atomic_t exit_indicator = 0;

void terminate(int /*signal*/) {
    exit_indicator = 1;
}
```

В обработчике сигналов нельзя делать “тяжёлые” вещи (логирование, аллокации, сложные вызовы), поэтому обычно ограничиваются установкой флага.

---

---

### sigaction() — регистрация обработчика сигнала

`sigaction()` — системный вызов POSIX для установки **обработчика сигнала**.
Это более надёжная и переносимая замена старому `signal()`.

```cpp
struct sigaction action;
memset(&action, 0, sizeof(struct sigaction)); // обнулить всю структуру
action.sa_handler = terminate;                // указать функцию-обработчик
sigaction(SIGTERM, &action, nullptr);         // повесить обработчик на SIGTERM
sigaction(SIGINT,  &action, nullptr);         // повесить обработчик на SIGINT
```

---

### struct sigaction

Структура, описывающая **поведение процесса при получении сигнала**.

Ключевые поля:

| Поле | Тип | Описание |
|---|---|---|
| `sa_handler` | `void (*)(int)` | Функция-обработчик (принимает номер сигнала) |
| `sa_mask` | `sigset_t` | Маска сигналов, блокируемых на время обработчика |
| `sa_flags` | `int` | Дополнительные флаги поведения |

Почему `memset(&action, 0, ...)`:
- Обнуляет `sa_mask` и `sa_flags` → никаких лишних блокировок, никаких спецрежимов.
- Без обнуления в `action` окажется мусор из стека — это UB.

---

### Третий аргумент sigaction() — oldact

```cpp
sigaction(SIGINT, &action, nullptr);
//                          ↑
//                 nullptr = нам не нужен старый обработчик
```

Если передать указатель на другую `struct sigaction`, туда запишется **предыдущий обработчик** сигнала.
Это позволяет при необходимости восстановить старое поведение.

---

### Почему обработчик принимает int

```cpp
void terminate(int signal) {
    g_flag = true;
}
```

ОС передаёт **номер сигнала**, который вызвал обработчик.
Это позволяет одной функцией обрабатывать несколько сигналов и при необходимости реагировать по-разному:

```cpp
void terminate(int signal) {
    if (signal == SIGTERM) { /* мягкое завершение */ }
    if (signal == SIGINT)  { /* Ctrl+C */ }
    g_flag = true;
}
```
---

### exit_indicator (флаг завершения)

`exit_indicator` — общий флаг, который читается в polling‑цикле:

```cpp
while (!exit_indicator) {
    // rte_eth_rx_burst() / обработка
}
```

Почему так делают:
- Polling‑циклы по дизайну бесконечные.
- Нужно уметь завершить программу “мягко”: остановить цикл, освободить mbuf, вызвать `rte_eal_cleanup()`.

Почему тип `volatile sig_atomic_t`:
- `sig_atomic_t` безопасен для записи в обработчике сигнала.
- `volatile` заставляет компилятор перечитывать значение из памяти, а не держать в регистре.

Если переходишь на многопоточность, часто делают отдельный stop‑флаг на `std::atomic_bool`, потому что `volatile` не даёт межпоточной синхронизации.

---

### Promiscuous Mode (Неразборчивый режим)
Режим работы NIC, при котором карта принимает **все** пакеты в сегменте сети,  
независимо от их MAC-адреса назначения (не только broadcast и собственные адреса).

## Аргументы rte_eal_init() (EAL parameters)

> Источник: [doc.dpdk.org/guides/linux_gsg/linux_eal_parameters.html](https://doc.dpdk.org/guides/linux_gsg/linux_eal_parameters.html)

`rte_eal_init()` принимает те же `argc` и `argv`, что и `main()`, и сам разбирает из них EAL-аргументы. Остаток (пользовательские аргументы) возвращается через скорректированные `argc`/`argv`.

### Как устроена командная строка DPDK

```
./app  [EAL-аргументы]  --  [аргументы самого приложения]
         ↑                  ↑
         rte_eal_init()      ваш код читает эту часть
         разбирает это
```

Разделитель `--` обязателен, если у приложения есть собственные аргументы. Если их нет — `--` всё равно писать можно (это безвредно).

## Группа 1: lcore (ядра CPU)

### --lcores / -l  [НУЖЕН]

Задаёт, какие логические ядра (lcore) будут у приложения и к каким физическим CPU их привязать.

Полный формат:

```
<lcores[@cpus]>[,<lcores[@cpus]>...]
```

- `lcore` — внутренний ID потока в DPDK (0, 1, 2, ...)
- `@cpus` — физический CPU ОС, к которому привязать поток
- Если `@` не указан — lcore ID == CPU ID

Примеры:

```bash
# Запустить 1 поток на физическом CPU 0. lcore id = 0
./app --lcores=0

# Запустить 3 потока: на CPU 1, 2 и 3. lcore id = 1, 2, 3
./app --lcores=1-3

# Явно: lcore 0 привязан к CPU 0, lcore 1 к CPU 1
./app --lcores=0,1

# lcore 1 привязан к CPU 31, lcore 2 к CPU 32
./app --lcores=1@31,2@32

# lcore 1 может бегать на любом из CPU 1 или 2 (ОС решает)
# ВНИМАНИЕ: производительность хуже, чем с жёсткой привязкой
./app --lcores='1@(1,2)'

# lcores 1,2,3 — все могут бегать на CPU 31, 32, 33 (без жёсткой привязки)
./app --lcores='(1-3)@(31-33)'
```

Важные ограничения:
- Если несколько lcore привязаны к одному физическому CPU — возможны дедлоки при использовании `rte_ring`, `rte_mempool`, спинлоков.

---

### --main-lcore  [ПОЛЕЗЕН]

Задаёт, какой lcore будет главным (на нём выполняется `main()`).

```bash
./app --lcores=0,1,2 --main-lcore=2
# main() будет выполняться на lcore 2 (CPU 2)
# lcore 0 и 1 — воркеры
```
По умолчанию главный первый из перечисленных.

---

### -R, --remap-lcore-ids  [СПЕЦИФИЧНЫЙ]

Автоматически переименовывает lcore-id в ряд начиная с 0 (или с заданного числа).

```bash
# Физические CPU 20-24, но lcore id будут 0-4
./app -l 20-24 -R
# Физические CPU 140-144, lcore id будут 10-14
./app -l 140-144 -R=10
```

Полезно, где "свободные" CPU имеют большие номера (например, 40-47), но внутри DPDK удобнее обращаться к ним как 0-7.

---

### -S, --service-corelist  [СПЕЦИФИЧНЫЙ]

Список lcore для системных сервисов DPDK (например, управление портами, таймеры).

```bash
./app --lcores=0,1,2 -S 2
# lcore 2 зарезервирован под сервисы DPDK
```

## Группа 2: устройства (NIC)

### -a, --allow  [ПОЛЕЗЕН]

Разрешить использование конкретного PCI-устройства. Только устройства из этого списка будут проинициализированы DPDK.

```bash
# Использовать только одну конкретную карту
./app --lcores=0 -n 4 -a 0000:00:1f.6 --

# Несколько устройств
./app --lcores=0 -n 4 -a 0000:00:1f.6 -a 0000:01:00.0 --
```

Формат адреса: `[domain:]bus:device.function` — это PCI-адрес устройства, который видно в выводе `lspci` или `dpdk-devbind.py --status`.

Нельзя использовать одновременно с `-b` (block).

---

| Аргумент | Для чего |
|---|---|
| `-b, --block`  [ПОЛЕЗЕН] |Запретить использование конкретного PCI-устройства. Все остальные будут инициализированы. |
| `--vdev` [СПЕЦИФИЧНЫЙ] |Добавить виртуальное устройство. Используется для тестирования без физической карты |


## Группа 3: память

### -n  [НУЖЕН]

Количество каналов памяти (memory channels). Влияет на то, как DPDK распределяет память между банками RAM для параллельного доступа.

```bash
./app --lcores=0 -n 4 --
```

---

### --numa-mem  [ПОЛЕЗЕН]

Заранее выделить указанный объём hugepage-памяти на каждом NUMA узле (в мегабайтах).

```bash
# 1GB на NUMA node 0, 2GB на NUMA node 1
./app --lcores=0 -n 4 --numa-mem 1024,2048 --
```

По умолчанию DPDK выделяет память по мере необходимости. 

---

### --huge-unlink  [СПЕЦИФИЧНЫЙ]

Управляет тем, что происходит с файлами hugepage в hugetlbfs при старте и завершении.

| Значение | Поведение |
|---|---|
| (не указан) / `existing` | Существующие файлы удаляются и пересоздаются — память очищена, утечек нет |
| `always` | Файлы всегда удаляются перед маппингом — не останется файлов в hugetlbfs |
| `never` | Файлы никогда не удаляются — hugepage переиспользуются от запуска к запуску, старт быстрее |

```bash
# Быстрый рестарт (hugepages не очищаются, могут содержать старые данные)
./app --lcores=0 -n 4 --huge-unlink=never --
```

Режим `never` ускоряет повторный запуск, но данные предыдущего процесса в памяти сохраняются.

---

| Аргумент | Для чего |
|---|---|
| `--huge-dir`  [ПОЛЕЗЕН] |Указать директорию `hugetlbfs` вместо автоматически определённой. По умолчанию  ищет смонтированную `hugetlbfs`. |
| `--numa-limit` [СПЕЦИФИЧНЫЙ] |Ограничить максимальный объём памяти на NUMA узел. |
| `--no-huge`  [СПЕЦИФИЧНЫЙ] | Не использовать hugepages — вместо этого использовать обычную анонимную память.|
| `--legacy-mem`  [СПЕЦИФИЧНЫЙ] | Включить старый (legacy) режим управления памятью DPDK. В старом режиме память выделяется единым блоком при старте. |
| `--single-file-segments`  [СПЕЦИФИЧНЫЙ] |  Создавать меньше файлов в hugetlbfs, объединяя сегменты. Работает только в не-legacy режиме.|
| `--match-allocations`  [СПЕЦИФИЧНЫЙ] | Освобождать hugepages обратно системе точно так же, как они были выделены изначально. |

## Группа 4: multiprocessing (несколько DPDK процессов)

### --file-prefix  [ПОЛЕЗЕН]

Задать уникальный префикс для разделяемых файлов DPDK-процесса. Позволяет запускать несколько независимых DPDK-приложений одновременно на одной машине.

```bash
# Первое приложение
./app1 --lcores=0 -n 4 --file-prefix=app1 --

# Второе приложение (другой префикс = отдельные hugepage файлы)
./app2 --lcores=1 -n 4 --file-prefix=app2 --
```

По умолчанию префикс `dpdk`. Если два процесса используют один и тот же префикс — они могут конфликтовать.

---

### --no-shconf  [СПЕЦИФИЧНЫЙ]

Не создавать разделяемые файлы конфигурации. Отключает поддержку вторичных DPDK-процессов.

## Группа 5: отладка и логирование

### --log-level  [ПОЛЕЗЕН]

Задать уровень логирования для компонентов DPDK.

```bash
# Включить debug-логи для EAL
./app --lcores=0 -n 4 --log-level lib.eal:debug --

# Включить debug для всех компонентов
./app --lcores=0 -n 4 --log-level .*:debug --

# Включить только для PMD (драйверы портов)
./app --lcores=0 -n 4 --log-level pmd:info --
```

Уровни логирования (от тихого к подробному):

| Уровень | Значение |
|---|---|
| `emerg` | Критическая системная ошибка |
| `alert` | Требуется немедленное вмешательство |
| `crit` | Критическая ошибка |
| `err` | Ошибка |
| `warning` | Предупреждение |
| `notice` | Важное сообщение |
| `info` | Информационное |
| `debug` | Отладочное (очень подробно) |

Можно указывать несколько раз для разных компонентов.

---

### --trace  [СПЕЦИФИЧНЫЙ]

Включить трассировку по имени компонента (regex). По умолчанию трассировка отключена.

```bash
# Трассировать только EAL
./app --lcores=0 -n 4 --trace=eal --

# Трассировать всё
./app --lcores=0 -n 4 --trace=.* --
```

---

### --trace-dir  [СПЕЦИФИЧНЫЙ]

Директория для файлов трассировки (по умолчанию — домашняя).

---

### --trace-bufsz  [СПЕЦИФИЧНЫЙ]

Максимальный размер буфера трассировки на поток.

---

### --trace-mode  [СПЕЦИФИЧНЫЙ]

Поведение при достижении лимита размера файла трассировки.

```bash
--trace-mode=overwrite   # (по умолчанию) перезаписывать старые данные
--trace-mode=discard     # отбрасывать новые данные, когда файл заполнен
```
