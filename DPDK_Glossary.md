## Словарик

Краткий справочник аббревиатур и базовых понятий.

| Термин | Расшифровка | Cмысл |
|---|---|---|
| **DPDK** | Data Plane Development Kit | Фреймворк Intel для быстрой обработки пакетов в сетевых приложениях |
| **NIC** | Network Interface Card | Сетевая карта — физическое устройство приёма/передачи пакетов |
| **[EAL](#eal-environment-abstraction-layer)** | Environment Abstraction Layer | Базовый слой DPDK: инициализация hugepages, ядер CPU, драйверов |
| **[PCI](#pcipcie-и-dma-как-пакет-попадает-в-ram)** | Peripheral Component Interconnect | Шина для подключения устройств (NIC, GPU и др.) к материнской плате |
| **[RX](#rx-queue-receive-queue)** | Receive | Приём пакетов (входящий трафик) |
| **[TX](#tx-queue-transmit-queue)** | Transmit | Передача пакетов (исходящий трафик) |
| **[mbuf](#rte_mbuf)** | Memory Buffer | Структура DPDK для хранения одного пакета в памяти |
| **[mempool](#rte_mempool)** | Memory Pool | Заранее выделенный набор буферов (mbuf) фиксированного размера |
| **[NUMA](#numa-non-uniform-memory-access)** | Non-Uniform Memory Access | Архитектура, где у каждого CPU есть "своя" быстрая память |
| **MAC** | Media Access Control | Уникальный аппаратный адрес сетевой карты (6 байт, напр. `08:00:27:95:BD:AE`) |
| **[VFIO](#vfio-pci)** | Virtual Function I/O | Механизм ядра Linux для прямого доступа к PCI-устройству из userspace |
| **[lcore](#lcore-в-dpdk)** | Logical Core | Логическое ядро CPU, к которому DPDK привязывает поток |
| **[Burst](#rte_eth_rx_burst)** | — | Пачка пакетов, обрабатываемых за один вызов (16/32/64 штуки) |
| **Kernel Bypass** | — | Обход ядра ОС — пакеты идут напрямую NIC → userspace без syscall |
| **[Polling](#polling-опрос)** | — | Активный опрос NIC в цикле вместо ожидания прерывания |
| **[CPU socket](#cpu-сокет-cpu-socket)** | — | Физический процессор (чип) на плате; в сервере может быть 1–2+ сокета |
| **[DMA](#pcipcie-и-dma-как-пакет-попадает-в-ram)** | Direct Memory Access | NIC пишет/читает данные напрямую в/из RAM без копирования через CPU |
| **[Hugepages](#страницы-памяти-tlb-и-hugepages)** | — | Большие страницы памяти (2MB/1GB), уменьшают нагрузку на TLB |
| **[TLB](#страницы-памяти-tlb-и-hugepages)** | Translation Lookaside Buffer | Кэш переводов виртуальных адресов в физические; TLB miss = лишняя задержка |
| **Atomic** | — | Атомарная операция: выполняется целиком, без “разрыва” другими потоками |


## Архитектура железа для DPDK

### CPU: физические и логические ядра

- **Физическое ядро** — физический блок, который находится внутри центрального процессора (CPU) и выполняет вычисления, обрабатывает команды и управляет потоками данных.
- **Логическое ядро (logical CPU)** — то, что видит ОС (CPU0, CPU1, ...). При SMT/Hyper-Threading одно физическое ядро обычно даёт 2 логических.

Важно: логические ядра одного физического делят многие ресурсы (часть конвейеров, кэши, порты исполнения), поэтому 2 логических не даст 2× производительность.

### SMT / Hyper-Threading

SMT работает так: в одном физическом ядре продублировано «архитектурное состояние» (регистры, счётчики, контекст), и ОС может планировать два потока так, будто это два отдельных процессора. 

Что остаётся общим (упрощённо):

```
Физическое ядро
├── Thread A (logical CPU X): регистры/контекст
├── Thread B (logical CPU Y): регистры/контекст
└── Общие ресурсы: execution units, L1/L2 (частично), доступ к L3/памяти
```

### Кэш CPU (L1/L2/L3) и latency

Кэш — это быстрая память рядом с ядром CPU, которая хранит недавно использованные данные.

```
RAM  (медленно)
 ↑
L3   (общий)
 ↑
L2   (на ядро)
 ↑
L1   (на ядро, самый быстрый)
```

Если поток мигрирует на другое ядро, «тёплый» кэш остаётся на старом ядре → на новом возникают cache miss (когда нужных данных нет в кэше и приходится идти в более медленную память) и скачки задержки.

### Affinity (привязка потока к ядру)

**Thread affinity** — запрет миграции потока между CPU-ядрами. DPDK делает это через EAL: ты явно задаёшь, на каких CPU запускать потоки, чтобы latency (задержка от прихода пакета до того, как ты смог его обработать) была стабильной.

### lcore в DPDK

Логическое ядро CPU, к которому DPDK привязывает поток исполнения.  
Привязка к конкретному ядру устраняет накладные расходы на переключение контекста и миграцию между ядрами.
DPDK использует термин **lcore** как «DPDK-ядро исполнения» (EAL thread), которому назначается `lcore_id`.


- Узнать текущий lcore: 

```cpp
unsigned id = rte_lcore_id();
```

- Перебрать активные lcore:

```cpp
uint16_t i = 0;
RTE_LCORE_FOREACH(i) {
    // i = lcore_id
}
```

### Как работает параметр --lcores

`--lcores` задаёт **маппинг**: какие lcore создать и к каким CPU (logical CPU ОС) их привязать. Формат: `<lcores[@cpus]>[,<lcores[@cpus]>...]`

Примеры из документации:

- `--lcores=1-3` — запустить потоки на CPU 1,2,3 с теми же lcore id. 

Для образовательных целей удобно думать так:

- `--lcores=0,1` → два потока DPDK: main на lcore 0 и worker на lcore 1 (как в примере 03).

### CPU-сокет (CPU socket)

**CPU-сокет** — это физический процессор как отдельный чип на материнской плате.
В сервере может быть 1 сокет (single-socket) или 2/4+ сокета (multi-socket).

Почему это важно для DPDK:
- У каждого сокета своя локальная память (RAM) и свои пути к устройствам (PCIe).
- Если поток крутится на сокете A, а память/устройство на сокете B, появляются лишние задержки.

### NUMA (Non-Uniform Memory Access) и сокеты

В NUMA-системах память «разделена по сокетам»: у каждого CPU-сокета есть своя локальная RAM.
Доступ к локальной памяти быстрее, а к памяти другого сокета — медленнее (и часто менее предсказуем).

Мини-схема:

```
Socket 0 (NUMA node 0)                Socket 1 (NUMA node 1)
+-----------------------+             +-----------------------+
| CPU cores + L3 cache  |             | CPU cores + L3 cache  |
| Memory controller     |             | Memory controller     |
| Local RAM             |             | Local RAM             |
+-----------------------+             +-----------------------+
            ^                                       ^
            |                                       |
            +--------     interconnect      --------+
                 remote memory = медленнее
```

Практика для DPDK (короткое правило):
- lcore (где крутится polling) + NIC + mempool должны быть на одном NUMA node.

Подсказки из кода DPDK:
- `rte_eth_dev_socket_id(port)` даёт NUMA node, где «сидит» NIC.
- `rte_socket_id()` даёт NUMA node текущего lcore.
- Если `rte_eth_dev_socket_id()` вернул -1 (неизвестно), используют `rte_socket_id()` как fallback.

### Каналы памяти (memory channels) и параметр -n

**Канал памяти** — физический «канал» между контроллером памяти CPU и планками RAM; больше каналов = выше пропускная способность памяти.

EAL-аргумент `-n <NUM>` задаёт число каналов памяти (исторически использовалось для модели распределения памяти/hugepages). В учебных примерах часто ставят `-n 2` или `-n 4`. 

### Страницы памяти, TLB и hugepages

ОС работает со страницами памяти (pages): чаще всего 4KB.
**TLB (Translation Lookaside Buffer)** — маленький, но очень быстрый кэш в CPU, который хранит соответствия «виртуальная страница → физическая страница».

Когда приложению нужно много разных страниц (например, большие mempool/ring/таблицы), TLB может не помещать все переводы — возникает **TLB miss** и CPU тратит время на обход таблиц страниц.

**Hugepages** (2MB или 1GB) уменьшают число страниц: меньше страниц → меньше переводов → ниже давление на TLB.
DPDK обычно использует hugepages для памяти под mbuf/mempool, чтобы сделать доступ к пакетным буферам стабильнее.

### PCI/PCIe и DMA: как пакет попадает в RAM

NIC подключена по PCIe и умеет делать **DMA** (Direct Memory Access): писать данные пакета напрямую в заранее подготовленные буферы в RAM (mbuf), без копирования через стек ядра. Это одна из причин низкой задержки в DPDK.

## Архитектура и инициализация
> Новые термины из примера `01-reading-a-packet-from-nic`

### EAL (Environment Abstraction Layer)
Уровень абстракции окружения — фундаментальный слой DPDK, который инициализирует всё необходимое для работы:  
выделяет [hugepages](#hugepages-большие-страницы-памяти), настраивает привязку потоков к ядрам CPU, инициализирует драйверы устройств.  
**Всегда вызывается первым** в любом DPDK-приложении.

```cpp
int32_t return_val = rte_eal_init(argc, argv);
if (return_val < 0) {
    std::cerr << "Unable to initialize DPDK EAL. Error: " << rte_errno << std::endl;
    exit(1);
}
```

**EAL-аргументы командной строки** передаются через `argc/argv` и разделяются от пользовательских аргументов символом `--`:
```
./app --lcores=0 -n 4 -- -s 1 -t 2
         ^EAL args^       ^user args^
```
- `--lcores=0` — использовать ядро CPU №0 для главного потока
- `-n 4` — использовать 4 канала памяти

📎 Документация: https://doc.dpdk.org/guides/linux_gsg/linux_eal_parameters.html

---

### rte_eal_init()
Функция инициализации EAL. Возвращает **количество обработанных EAL-аргументов**.  
После вызова нужно скорректировать `argc` и `argv`, чтобы они указывали на пользовательские аргументы:

```cpp
// До вызова: argc=9, argv = ["./app", "--lcores=0", "-n", "4", "--", "-s", "1", "-t", "2"]
int32_t return_val = rte_eal_init(argc, argv); // вернёт 4
argc -= return_val; // argc = 5  ("--", "-s", "1", "-t", "2")
argv += return_val; // argv теперь указывает на "--"
```

---

### rte_eal_cleanup()
Освобождает все ресурсы, выделенные EAL. Должна вызываться перед завершением программы.

```cpp
rte_eal_cleanup();
return 0;
```

---

### rte_errno
Глобальная переменная DPDK для хранения кода последней ошибки (аналог стандартного `errno`).  
Используется для диагностики при неудачной инициализации EAL и других операциях.

```cpp
if (return_val < 0) {
    std::cerr << "Error code: " << rte_errno << std::endl;
}
```

## Порты и очереди

### Port (Ethernet Port)
В терминологии DPDK **порт** — это сетевой интерфейс (NIC),  
привязанный к DPDK-драйверу (например, `vfio-pci`). Идентифицируется числовым `port_id`.

```cpp
uint16_t port_ids[RTE_MAX_ETHPORTS] = {0};
int16_t total_port_count = 0;

RTE_ETH_FOREACH_DEV(id) {
    port_ids[total_port_count] = id;
    total_port_count++;
}
```

---

### RTE_ETH_FOREACH_DEV
Макрос для итерации по всем доступным Ethernet-портам в системе.

```cpp
int16_t id = 0;
RTE_ETH_FOREACH_DEV(id) {
    // id принимает значения 0, 1, 2, ... для каждого найденного порта
}
```

---

### RTE_MAX_ETHPORTS
Константа — максимально допустимое число Ethernet-портов в одном DPDK-приложении.  
Используется для ограничения размера массива `port_ids`.

---

### RX Queue (Receive Queue)
Очередь приёма пакетов на уровне NIC. Каждый порт может иметь несколько RX-очередей  
(Multi-Queue), что позволяет параллельно обрабатывать пакеты на разных CPU-ядрах.  
В этом примере используется одна RX-очередь.

```cpp
const uint16_t rx_queues = 1;
const uint16_t tx_queues = 0; // TX не нужен — только читаем
```

---

### TX Queue (Transmit Queue)
Очередь передачи пакетов. В примере `01-reading-a-packet-from-nic` не используется (`tx_queues = 0`),  
так как задача только в чтении пакетов.

---

### rte_eth_dev_configure()
Конфигурирует Ethernet-порт: задаёт число RX/TX очередей и режим их работы.

```cpp
rte_eth_conf portConf = {
    .rxmode = { .mq_mode = RTE_ETH_MQ_RX_NONE }, // одна очередь, без балансировки
    .txmode = { .mq_mode = RTE_ETH_MQ_TX_NONE }
};

return_val = rte_eth_dev_configure(port_ids[0], rx_queues, tx_queues, &portConf);
```

---

### RTE_ETH_MQ_RX_NONE
Режим одиночной очереди приёма — пакеты не распределяются между несколькими очередями.  
Альтернативы: `RTE_ETH_MQ_RX_RSS` (распределение по хэшу), `RTE_ETH_MQ_RX_DCB` и др.

---

### rte_eth_rx_queue_setup()
Настраивает конкретную RX-очередь порта: задаёт глубину очереди (число дескрипторов)  
и привязывает её к memory pool для хранения принятых пакетов.

```cpp
return_val = rte_eth_rx_queue_setup(
    port_ids[0],   // port_id
    i,             // queue_id (0, 1, 2, ...)
    256,           // nb_desc: глубина очереди (число дескрипторов)
    portSocketId,  // socket_id: NUMA-узел
    nullptr,       // rx_conf: NULL = использовать дефолтную конфигурацию
    memory_pool    // mb_pool: пул памяти для пакетов
);
```

---

### rte_eth_promiscuous_enable()
Включает **promiscuous mode** (неразборчивый режим) на порту.  
В этом режиме NIC принимает **все** пакеты в сети, не только адресованные её MAC-адресу.  
Полезно для мониторинга трафика и сниффинга.

```cpp
return_val = rte_eth_promiscuous_enable(port_ids[0]);
// Не все драйверы поддерживают — ошибку можно игнорировать
```

---

### rte_eth_dev_start()
Запускает Ethernet-порт после его конфигурации. После вызова порт начинает принимать пакеты.

```cpp
return_val = rte_eth_dev_start(port_ids[0]);
```

---

### rte_eth_dev_socket_id()
Возвращает NUMA socket ID, к которому физически подключена сетевая карта.  
Важно для оптимизации: memory pool желательно создавать на том же NUMA-узле, что и NIC,  
чтобы избежать медленного cross-socket доступа к памяти.

```cpp
const int16_t portSocketId = rte_eth_dev_socket_id(port_ids[0]);
const int16_t coreSocketId = rte_socket_id(); // NUMA-узел текущего ядра CPU
// Используем тот, что >= 0 (валидный)
int16_t socketId = (portSocketId >= 0) ? portSocketId : coreSocketId;
```

## Управление памятью

### Hugepages (Большие страницы памяти)

См. также: [Страницы памяти, TLB и hugepages](#страницы-памяти-tlb-и-hugepages).
Стандартная страница памяти Linux — 4KB. DPDK использует страницы по **2MB или 1GB**,  
что резко снижает количество промахов TLB и ускоряет доступ к большим буферам пакетов.

Настройка (из Задания №2):
```bash
echo 1024 | sudo tee /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages
# Выделяем 1024 hugepages по 2MB = 2GB под DPDK
```

---

### rte_mempool
Структура пула памяти DPDK — заранее выделенный набор буферов фиксированного размера.  
Используется для хранения принятых пакетов (объектов `rte_mbuf`).  
Пул создаётся один раз и переиспользуется, избегая динамического `malloc`/`free`.

```cpp
rte_mempool *memory_pool = rte_pktmbuf_pool_create(
    "mempool_1",             // имя пула (уникальное)
    1023,                    // число буферов в пуле
    512,                     // cache_size: кэш на lcore для скорости аллокации
    0,                       // priv_size: приватные данные на mbuf (не нужны)
    RTE_MBUF_DEFAULT_BUF_SIZE, // размер одного буфера = 2048 + 128 байт
    rte_socket_id()          // NUMA-узел
);
```

> Число буферов `1023` не просто так. Для оптимальной работы mempool рекомендуется  
> использовать значения вида `2^n - 1` (степень двойки минус один).

---

### rte_mbuf
Структура, описывающая один сетевой пакет в DPDK. Содержит метаданные пакета  
и указатель на буфер с сырыми данными.

Ключевые поля:
| Поле | Тип | Описание |
|---|---|---|
| `data_len` | `uint16_t` | Длина данных в этом сегменте |
| `pkt_len` | `uint32_t` | Общая длина пакета (все сегменты) |
| `nb_segs` | `uint8_t` | Число сегментов (обычно 1) |
| `port` | `uint16_t` | ID порта, с которого пришёл пакет |
| `buf_addr` | `void*` | Указатель на буфер данных |

```cpp
rte_mbuf *received_packets[32];
// После rte_eth_rx_burst() каждый элемент массива — указатель на принятый пакет
std::cout << "Packet length: " << received_packets[i]->data_len << std::endl;
```

---

### RTE_MBUF_DEFAULT_BUF_SIZE
Константа = **2176 байт** (2048 + 128). Стандартный размер буфера для одного пакета:
- `2048` байт — данные пакета (достаточно для стандартного Ethernet MTU = 1500 байт)
- `128` байт — заголовок `rte_mbuf` и служебные данные

---

### rte_pktmbuf_free_bulk()
Освобождает массив `rte_mbuf` обратно в memory pool за один вызов.  
Важно освобождать пакеты после обработки, иначе пул закончится.

```cpp
rte_pktmbuf_free_bulk(received_packets, rx_packets);
```

## Приём пакетов

### rte_eth_rx_burst()
Ключевая функция для получения пакетов — **вытаскивает пачку (burst) пакетов**  
из RX-очереди NIC в массив `rte_mbuf`. Возвращает фактическое число принятых пакетов.

```cpp
rte_mbuf *received_packets[32]; // буфер под 32 пакета
uint16_t rx_packets = rte_eth_rx_burst(
    port_ids[0],       // port_id
    0,                 // queue_id
    received_packets,  // массив для записи указателей на пакеты
    32                 // максимум пакетов за один вызов
);
```

> **Burst-обработка** — вместо обработки пакетов по одному   берём сразу пачку (16, 32, 64...). Это амортизирует накладные расходы на вызов функции  и улучшает использование кэша CPU.

---

### Polling (Опрос)
Вместо прерываний (interrupt-driven I/O) DPDK использует **активный опрос** NIC в цикле.  
Поток непрерывно вызывает `rte_eth_rx_burst()`, проверяя наличие новых пакетов.  
Это устраняет задержку от обработки прерываний (~microseconds).

```cpp
while (!exit_indicator) {
    rx_packets = rte_eth_rx_burst(port_ids[0], 0, received_packets, 32);

    if (rx_packets == 0) {
        std::this_thread::sleep_for(10us); // небольшая пауза при отсутствии пакетов
        continue;
    }
    // обработка пакетов...
}
```

> `sleep_for(10us)` показан для примера.

## Системные концепции

### vfio-pci
Модуль ядра Linux для прямого доступа к PCI-устройствам из пространства пользователя (**kernel bypass**). DPDK использует его для управления NIC без участия ОС-драйвера,  
что исключает накладные расходы на системные вызовы.

```bash
sudo modprobe vfio-pci
sudo ./dpdk-devbind.py -b vfio-pci 0000:00:1f.6
```

---

### dpdk-devbind.py
Утилита DPDK для привязки/отвязки сетевых устройств от драйверов.

```bash
./dpdk-devbind.py --status          # показать все устройства и их текущие драйверы
./dpdk-devbind.py -b vfio-pci 0000:00:1f.6   # привязать устройство к DPDK-драйверу
./dpdk-devbind.py -b e1000 0000:00:1f.6      # вернуть обратно к ОС-драйверу
```

### Atomic (атомарность)

**Атомарная операция** — это такая операция над данными, которая выглядит для других потоков как неделимая: либо она ещё не началась, либо уже полностью завершена.

Зачем это нужно:
- Чтобы несколько потоков могли безопасно менять общие счётчики/флаги без мьютексов.
- Чтобы строить lock-free структуры (например, кольцевые буферы), где нет блокировок.

Важно не путать:
- `volatile` **не делает** операции атомарными и не даёт межпоточной синхронизации.
- `std::atomic<T>` (C++) или атомики в DPDK дают атомарность и (при нужном memory order) упорядочивание.

---

### Signals (сигналы ОС)

**Сигнал** — это асинхронное уведомление процессу от ОС (или другого процесса/терминала).
Сигналы полезны, чтобы корректно завершать бесконечные polling‑циклы.

Частые сигналы:
- `SIGINT` — прерывание с терминала (обычно Ctrl+C).
- `SIGTERM` — “попросить завершиться” (например, `kill <pid>` без `-9`).
- `SIGKILL` — “убить сразу” (его нельзя перехватить обработчиком).


---

### terminate() (обработчик сигнала)

`terminate()` в примере — это функция, которую ОС вызывает, когда процесс получил `SIGINT` или `SIGTERM`.
Её задача — **быстро** выставить флаг остановки и выйти.

```cpp
static volatile sig_atomic_t exit_indicator = 0;

void terminate(int /*signal*/) {
    exit_indicator = 1;
}
```

В обработчике сигналов нельзя делать “тяжёлые” вещи (логирование, аллокации, сложные вызовы), поэтому обычно ограничиваются установкой флага.

---

### exit_indicator (флаг завершения)

`exit_indicator` — общий флаг, который читается в polling‑цикле:

```cpp
while (!exit_indicator) {
    // rte_eth_rx_burst() / обработка
}
```

Почему так делают:
- Polling‑циклы по дизайну бесконечные.
- Нужно уметь завершить программу “мягко”: остановить цикл, освободить mbuf, вызвать `rte_eal_cleanup()`.

Почему тип `volatile sig_atomic_t`:
- `sig_atomic_t` безопасен для записи в обработчике сигнала.
- `volatile` заставляет компилятор перечитывать значение из памяти, а не держать в регистре.

Если переходишь на многопоточность, часто делают отдельный stop‑флаг на `std::atomic_bool`, потому что `volatile` не даёт межпоточной синхронизации.

---

### Promiscuous Mode (Неразборчивый режим)
Режим работы NIC, при котором карта принимает **все** пакеты в сегменте сети,  
независимо от их MAC-адреса назначения (не только broadcast и собственные адреса).
