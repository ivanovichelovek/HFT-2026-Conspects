## Словарик

Краткий справочник терминов, которые появляются в заданиях и статье tls.dxdt.ru.

### Основы протокола

| Термин | Расшифровка | Смысл |
|---|---|---|
| **TLS** | Transport Layer Security | Протокол защищённого канала поверх TCP. Обеспечивает три гарантии: конфиденциальность (данные зашифрованы), целостность (подмена обнаружима), аутентификация (сервер тот, за кого себя выдаёт). Используется в HTTPS, SMTPS, IMAPS и других протоколах. |
| **SSL** | Secure Sockets Layer | Исторический предшественник TLS, разработанный Netscape в 1994–96 гг. SSL 2.0 и 3.0 признаны небезопасными и запрещены (RFC 7568). Сегодня «SSL» — просто разговорный синоним TLS. |
| **Record (запись)** | TLS Record | Базовая единица транспорта TLS: 5-байтовый заголовок (тип + версия + длина) плюс данные. Всё в TLS передаётся в записях. |
| **Record layer** | Уровень записей | Нижний слой TLS, отвечающий за разбивку данных на записи, шифрование и добавление тега аутентификации. Поверх него работают Handshake, Alert и Application Data. |
| **Cipher suite** | Криптонабор | Строка вида `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`, описывающая все алгоритмы сессии: обмен ключами + аутентификация + шифр + хеш. В TLS 1.3 список сокращён до 5 наборов, все без устаревших алгоритмов. |
| **Alert** | — | Служебное сообщение об ошибке или предупреждении. Бывает `warning` (соединение может продолжиться) и `fatal` (соединение немедленно закрывается). В TLS 1.3 тип Alert скрыт внутри зашифрованной записи. |
| **Session ticket** | Тикет сессии | Зашифрованный «билет», который сервер выдаёт клиенту в конце сессии. При следующем подключении клиент предъявляет тикет и пропускает полный Handshake. Альтернатива Session ID. |
| **0-RTT** | Zero Round-Trip Time | Режим возобновления сессии в TLS 1.3: клиент отправляет данные приложения прямо в первом пакете ClientHello, не дожидаясь ответа. Уязвим к replay-атаке — данные могут быть воспроизведены злоумышленником. |

### Шифры, ключи и режимы

| Термин | Расшифровка | Смысл |
|---|---|---|
| **Симметричное шифрование** | — | Шифрование, где один и тот же ключ используется для зашифрования и расшифрования. Быстро (гигабиты в секунду с AES-NI), но требует предварительного согласования ключа. Примеры: AES, ChaCha20. |
| **Асимметричное шифрование** | — | Шифрование с парой ключей: открытый (публичный) и закрытый (приватный). Открытым шифруют или проверяют подпись, закрытым — расшифровывают или подписывают. Медленнее симметричного в ~1000 раз. Примеры: RSA, ECDSA. |
| **Public key** | Открытый ключ | Часть ключевой пары, которую можно свободно публиковать. Используется для шифрования данных владельцу или проверки его подписи. |
| **Private key** | Закрытый ключ | Секретная часть ключевой пары. Никогда не передаётся по сети. Используется для расшифровки или создания подписи. |
| **Ephemeral key** | Эфемерный ключ | Временная ключевая пара, создаваемая заново для каждой сессии и удаляемая после её завершения. Буква «E» в ECDHE/DHE. Обеспечивает forward secrecy. |
| **RSA** | Rivest–Shamir–Adleman | Асимметричный алгоритм на основе сложности факторизации произведения двух больших простых чисел. В TLS применяется для подписи сертификатов и (устаревший вариант) для передачи premaster secret. Минимально безопасный размер ключа — 2048 бит. |
| **DHE / ECDHE** | (Elliptic Curve) Diffie–Hellman Ephemeral | Протокол согласования общего секрета: стороны обмениваются открытыми значениями, каждая вычисляет один и тот же секрет, не передавая его по сети. ECDHE — вариант на эллиптических кривых (компактнее и быстрее классического DHE). |
| **ECDSA** | Elliptic Curve Digital Signature Algorithm | Алгоритм электронной подписи на эллиптических кривых. Используется в сертификатах и для подписи Handshake-параметров. 256-битный ключ ECDSA по стойкости эквивалентен 3072-битному RSA. |
| **Эллиптическая кривая** | Elliptic curve | Множество точек вида `y² = x³ + ax + b` с определённой операцией «сложения». Безопасность основана на сложности задачи дискретного логарифма на кривой (ECDLP). Популярные кривые: `secp256r1` (P-256), `secp384r1`, `X25519`. |
| **Premaster secret** | — | Промежуточный секрет, вычисляемый обеими сторонами в результате ECDHE-обмена. Никогда не передаётся напрямую по сети — стороны вычисляют одинаковое значение независимо. |
| **Master secret** | — | 48-байтовый основной секрет сессии в TLS 1.2, получаемый из premaster secret и случайных чисел клиента/сервера через PRF. Из него выводятся все рабочие ключи. |
| **Session keys** | Сеансовые ключи | Симметричные ключи для шифрования трафика. Используются парами: отдельный ключ для каждого направления (client→server и server→client). |
| **PRF** | Pseudorandom Function | Псевдослучайная функция, используемая в TLS для вывода master secret и ключевого материала из входных данных. В TLS 1.2 построена на SHA-256; в TLS 1.3 заменена на HKDF. |
| **HKDF** | HMAC-based Key Derivation Function | Стандартный алгоритм вывода ключей (RFC 5869), используемый в TLS 1.3. Состоит из двух шагов: Extract (сжать энтропию в один секрет) и Expand (развернуть в нужное количество ключевого материала). |
| **KDF** | Key Derivation Function | Общее название для функций вывода ключей: принимают «сырую» энтропию (shared secret) и выдают готовые симметричные ключи. PRF и HKDF — конкретные реализации KDF. |
| **Forward secrecy** | Прямая секретность | Свойство протокола: компрометация долгосрочного ключа сервера (из сертификата) не позволяет расшифровать прошлые сессии. Обеспечивается за счёт эфемерных ECDHE-ключей, которые удаляются после сессии. |
| **AES** | Advanced Encryption Standard | симметричный алгоритм блочного шифрования, принятый в качестве мирового стандарта защиты данных. Он шифрует данные блоками по 128 бит, используя ключи длиной 128, 192 или 256 бит, что обеспечивает высокую безопасность и скорость работы. |
| **ChaCha20** | — | Симметричный потоковый шифр от Бернштейна. Не требует аппаратного ускорения — быстр на любом процессоре (мобильники, IoT). В TLS используется в паре с аутентификатором Poly1305. |
| **GCM** | Galois/Counter Mode | Режим AEAD для AES: шифрует данные в режиме счётчика (CTR) и одновременно вычисляет тег аутентификации через умножение в поле GF(2¹²⁸). Основной режим в современном TLS. |
| **CBC** | Cipher Block Chaining | Режим блочного шифра: каждый блок XOR-ится с предыдущим зашифрованным блоком. Уязвим к padding oracle атакам (BEAST, Lucky 13, POODLE). В TLS 1.3 запрещён. |
| **AEAD** | Authenticated Encryption with Associated Data | Класс режимов шифрования, совмещающих конфиденциальность и аутентификацию в одной операции. Нельзя расшифровать без одновременной проверки целостности. Примеры: AES-GCM, ChaCha20-Poly1305. Единственный тип, разрешённый в TLS 1.3. |
| **HMAC** | Hash-based Message Authentication Code | Код аутентификации сообщения на основе хеш-функции и секретного ключа: `HMAC(key, msg) = H((key ⊕ opad) ∥ H((key ⊕ ipad) ∥ msg))`. В TLS 1.2 используется в PRF и для проверки целостности записей в CBC-режиме. |
| **MAC / Auth Tag** | Message Authentication Code | Код аутентификации — «цифровая пломба», позволяющая получателю обнаружить изменение данных. В AEAD-режимах называется тегом аутентификации (auth tag), обычно 16 байт. |
| **Nonce (IV)** | Number used once | Уникальное значение, используемое ровно один раз для данного ключа. В AES-GCM нонс 96 бит: обычно 32-битный «соль» (из key block) + 64-битный счётчик записей. Повтор нонса при том же ключе катастрофически ломает безопасность GCM. |
| **AAD** | Additional Authenticated Data | Данные, которые аутентифицируются, но не шифруются. В TLS это заголовок записи: тип, версия, длина, номер последовательности. Получатель проверяет их через тег аутентификации. |
| **Sequence number** | Порядковый номер | Счётчик записей (начинается с 0), отдельный для каждого направления. Входит в AAD и используется при построении нонса. Защищает от вырезания и переупорядочивания записей. |
| **Padding** | Дополнение | В TLS 1.3 — нулевые байты, добавляемые в конец plaintext записи для маскировки реальной длины сообщения. Получатель обрезает их при расшифровке. |

### Логика handshake

| Термин | Расшифровка | Смысл |
|---|---|---|
| **Handshake** | — | Фаза переговоров перед передачей данных: клиент и сервер договариваются о версии TLS, шифронаборе, обмениваются ключами и проверяют сертификаты. В TLS 1.2 занимает 2 round-trip, в TLS 1.3 — 1. |
| **ClientHello** | — | Первое сообщение клиента — версия TLS, случайные nonce, список шифронаборов. Запускает Handshake. |
| **ServerHello** | — | Ответ сервера — выбранная версия TLS, nonce сервера, выбранный шифронабор. Подтверждает параметры сессии. |
| **Certificate** | — | Сертификат сервера (цепочка до **CA**): клиент проверяет подлинность сервера через доверенные корневые сертификаты. |
| **CertificateVerify** | — | Подпись сервером своих сертификатов с использованием приватного ключа: доказывает владение приватным ключом, соответствующим публичному в сертификате. |
| **ChangeCipherSpec** | - | Служебное сообщение (не Handshake!), сигнализирующее переход к зашифрованному режиму. В TLS 1.3 передаётся только как «пустышка» для совместимости с промежуточными узлами. |
| **Finished** | — | Первое зашифрованное Handshake-сообщение. Содержит хеш всех предыдущих Handshake-сообщений — криптографическое подтверждение того, что переговоры не были подменены. |
| **HelloRetryRequest** | — | Сервер запрашивает повторный **ClientHello** с нужным **key_share**, если клиент предложил неподдерживаемый алгоритм. Добавляет 1 round-trip для согласования. |
| **ServerKeyExchange** | — | Сервер отправляет свои **DH/ECDHE** параметры для генерации общего секрета. |
| **key_share** | — | Расширение ClientHello/ServerHello в TLS 1.3: клиент отправляет ECDHE-ключ прямо в первом сообщении. Позволяет вычислить shared secret за 1 round-trip вместо 2. |
| **Session ID** | — | Идентификатор сессии, выдаваемый сервером: при повторном подключении клиент предъявляет его и пропускает полный Handshake |
| **Session Ticket** | — | Зашифрованный сервером билет с мастер-ключом сессии: клиент хранит его и использует для возобновления сессии без полного Handshake. Более эффективен **Session ID**. |
| **PSK** | **Pre-Shared Key** | Предварительно согласованный ключ (**0-RTT**): позволяет возобновить сессию без полного обмена ключами. Риск replay-атак в TLS 1.3 решается nonce. |
| **SNI** | **Server Name Indication** | Расширение ClientHello: клиент сообщает имя хоста в открытом виде до начала шифрования. Позволяет одному IP-адресу обслуживать несколько HTTPS-сайтов. Утечка: провайдер видит, к какому домену подключается клиент. |
| **ALPN** | **Application-Layer Protocol Negotiation** | Расширение TLS: клиент сообщает список поддерживаемых прикладных протоколов (`http/1.1`, `h2`, `h3`), сервер выбирает один. Позволяет мультиплексировать разные протоколы на одном порту без дополнительного round-trip. |
| **ECH** | **Encrypted Client Hello** | Расширение TLS 1.3: весь ClientHello шифруется открытым ключом сервера, заранее опубликованным в DNS. Скрывает SNI и другую метаинформацию Handshake от наблюдателя. |

### Сертификаты

| Термин | Расшифровка | Смысл |
|---|---|---|
| **Certificate** | Сертификат X.509 | Файл, связывающий открытый ключ с именем владельца и подписанный вышестоящим CA. Клиент проверяет подпись CA и убеждается, что открытый ключ действительно принадлежит данному домену. |
| **X.509** | — | Стандарт формата цифровых сертификатов (RFC 5280). Определяет поля: Subject, Issuer, Serial Number, Validity, Subject Public Key Info, Extensions и Signature. |
| **CSR** | Certificate Signing Request | Запрос на подпись сертификата: файл с открытым ключом и реквизитами владельца, подписанный соответствующим приватным ключом. Отправляется в CA, который выпускает сертификат. |
| **CA** | Certificate Authority | Удостоверяющий центр: организация, подписывающая сертификаты своим ключом. Браузер/ОС доверяет набору ~150 корневых CA. |
| **Root CA** | Корневой УЦ | CA верхнего уровня. Его сертификат самоподписан и хранится в доверенном хранилище ОС/браузера. Обычно не подписывает сертификаты напрямую — делает это через промежуточные CA. |
| **Intermediate CA** | Промежуточный УЦ | CA, чей сертификат подписан Root CA. Подписывает конечные сертификаты серверов. Используется для изоляции риска: если скомпрометирован, отзывается только промежуточный CA, а не корневой. |
| **Certificate chain** | Цепочка сертификатов | Последовательность: сертификат сервера → промежуточный CA → Root CA. Сервер присылает сертификат + промежуточные CA. Клиент строит цепочку до доверенного Root CA. |
| **PKI** | Public Key Infrastructure | Инфраструктура открытых ключей: совокупность Root CA, промежуточных CA, политик выпуска/отзыва, списков CRL и протоколов OCSP. |
| **CRL** | Certificate Revocation List | Список отозванных сертификатов, публикуемый CA. Клиент должен периодически загружать CRL и проверять, не попал ли сертификат сервера в список. Медленно и ненадёжно — вытесняется OCSP. |
| **OCSP** | Online Certificate Status Protocol | Протокол для проверки статуса сертификата в реальном времени: клиент спрашивает OCSP-сервер CA «действителен ли сертификат с таким серийным номером?» |
| **OCSP Stapling** | — | Оптимизация: сервер сам заранее запрашивает OCSP-ответ у CA и «прикалывает» (staples) его к Handshake. Клиенту не нужно делать отдельный запрос к CA — быстрее и приватнее. |

### AES (Advanced Encryption Standard)

| Термин | Расшифровка | Смысл |
|---|---|---|
| **State** | — | 4×4 матрица байтов (128 бит), основная структура данных AES. Представляет блок открытого текста или промежуточное состояние. |
| **Word** | — | Столбец State (4 байта). Используется при XOR с подключом раунда в AddRoundKey. |
| **S-box** | Substitution box | Нелинейная таблица замены 8-бит → 8-бит (256 входов). Гарантирует стойкость к линейному криптоанализу. |
| **GF(2⁸)** | Галусово поле 256 | Конечное поле для MixColumns: арифметика XOR + умножение по логарифмическим таблицам. |
| **SubBytes** | — | Замена каждого байта State через S-box. Первый и нелинейный шаг раунда. |
| **ShiftRows** | — | Циклический сдвиг строк State: 0,1,2,3 байта влево для строк 1,2,3,4. Обеспечивает диффузию по строкам. |
| **MixColumns** | — | Линейное преобразование столбцов State (умножение на матрицу в GF(2⁸)). Обеспечивает диффузию по столбцам. |
| **AddRoundKey** | — | XOR всего State с 128-битным подключом текущего раунда. То место, которое делает шифрование уникальным благодаря ключу. |
| **Round key** | Подключ раунда | 128 бит, получаемые расширением основного ключа для каждого раунда. |
| **Key expansion** | Расширение ключа | Алгоритм генерации подключей для каждого раунда шифрования из основного ключа. |
| **Cipher block** | Блок шифра | 128 бит (16 байт) входных данных для AES. Преобразуется в State при начале шифрования. |
| **Nr** | Number of rounds | Количество раундов: 10 для AES-128, 12 для AES-192, 14 для AES-256. |
| **Nk** | Number of key words | Длина ключа в 32-битных словах: 4 (128 бит), 6 (192 бит), 8 (256 бит). |

### Атаки

| Термин | Расшифровка | Смысл |
|---|---|---|
| **MITM** | Man-in-the-Middle | Атака «человек посередине»: злоумышленник перехватывает трафик между клиентом и сервером, читает или подменяет его. TLS предотвращает через проверку сертификатов — без доверенного сертификата MITM невозможен. |
| **Downgrade attack** | Атака понижения версии | Злоумышленник принуждает обе стороны использовать старую уязвимую версию TLS или слабый шифронабор. Защита — сообщение Finished (хеш всех Handshake-сообщений) и в TLS 1.3 раннее подписание параметров. |
| **Padding oracle** | — | Класс атак на CBC-режим: сервер по-разному реагирует на ошибки паддинга, что позволяет расшифровать данные побайтно без знания ключа. Основа атак BEAST, Lucky 13, POODLE. |
| **BEAST** | Browser Exploit Against SSL/TLS | Атака 2011 года на TLS 1.0 CBC: использует предсказуемый IV в CBC-режиме для расшифровки трафика. Закрыта переходом на TLS 1.2+ и GCM. |
| **POODLE** | Padding Oracle On Downgraded Legacy Encryption | Атака 2014 года на SSLv3 CBC: использует padding oracle для расшифровки. SSLv3 полностью отключён. |
| **FREAK** | Factoring RSA Export Keys | Атака 2015 года: принуждение к слабым экспортным RSA-ключам (512 бит), которые факторизовались за несколько часов. Закрыта удалением экспортных шифронаборов. |
| **Logjam** | — | Атака 2015 года: принуждение к 512-битным DH-параметрам, заранее просчитанным атакующим. Закрыта требованием DH ≥ 2048 бит или переходом на ECDHE. |
| **Heartbleed** | CVE-2014-0160 | Уязвимость реализации в OpenSSL: ошибка в расширении Heartbeat позволяла читать до 64 КБ памяти сервера за один запрос, включая приватные ключи. Не атака на протокол, а баг в коде. |
| **Replay attack** | Атака повтора | Злоумышленник перехватывает и повторно отправляет легитимный запрос. Актуально для 0-RTT в TLS 1.3: данные первого пакета могут быть воспроизведены, поэтому 0-RTT нельзя использовать для неидемпотентных операций. |

### Постквантовая криптография

| Термин | Расшифровка | Смысл |
|---|---|---|
| **Post-quantum** | Постквантовая криптография | Алгоритмы, устойчивые к атакам на квантовых компьютерах. Алгоритм Шора взламывает RSA и ECDSA за полиномиальное время. AES-256 выдерживает (алгоритм Гровера только удваивает сложность перебора). |
| **ML-KEM** | Module Lattice Key Encapsulation Mechanism | Постквантовый алгоритм инкапсуляции ключей (бывший CRYSTALS-Kyber), стандартизованный NIST в 2024 году. Внедряется в TLS 1.3 через расширение `key_share` для защиты обмена ключами. |
| **Harvest now, decrypt later** | «Собирай сейчас, расшифруй потом» | Стратегия атаки: перехватить и сохранить зашифрованный трафик сегодня, а расшифровать когда появятся квантовые компьютеры. Мотивирует переход на постквантовые алгоритмы уже сейчас. |

## Назначение TLS

TLS создаёт защищённый канал поверх уже установленного TCP-соединения. Протокол решает три задачи одновременно:

- **Конфиденциальность** — данные шифруются симметричным шифром (AES-GCM или ChaCha20-Poly1305); перехватчик видит только псевдослучайный шум.
- **Целостность** — каждая запись сопровождается тегом аутентификации (auth tag); любое изменение байта в пути обнаруживается получателем.
- **Аутентификация** — сервер доказывает свою подлинность сертификатом, подписанным доверенным CA; клиент убеждается, что говорит именно с нужным хостом.

Важно понимать, что TLS **не** обеспечивает доступность (DDoS — за пределами его компетенции) и **не** защищает данные после того, как они расшифрованы на конечном узле. Если сервер скомпрометирован — TLS бесполезен.

TLS не скрывает и сам факт соединения: IP-адреса, порты, приблизительный объём трафика и временны́е паттерны видны пассивному наблюдателю даже без расшифровки.

---

## Модель угроз и цели

TLS проектировался из предположения, что **сеть полностью враждебна**: атакующий может перехватывать, задерживать, дублировать, удалять и подменять любые пакеты. Из этого следуют конкретные требования к протоколу.

**Что TLS защищает:**

- Содержимое передаваемых данных (payload).
- Параметры Handshake от подмены (сообщение Finished).
- Идентификацию сервера через цепочку сертификатов.

**Что TLS не защищает (и почему это важно знать):**

- **Метаданные соединения** — наблюдатель видит IP-адреса, SNI (в TLS < 1.3), размеры записей, тайминги запросов. По этим данным можно установить, с каким сервисом общается клиент, и даже угадать тип действий (логин, покупка, просмотр видео).
- **Длину полезной нагрузки** — шифрование не меняет размер данных. Запрос на 1 байт и на 10 КБ различимы без расшифровки. Padding в TLS 1.3 частично решает эту проблему.
- **Endpoints** — если клиент или сервер скомпрометирован (кейлоггер, RCE, XSS), TLS бесполезен.
- **Корректность реализации** — Heartbleed (2014) украл приватные ключи не через атаку на протокол, а через баг в коде OpenSSL.

**Устойчивость к даунгрейду** — отдельная важная задача. Без защиты злоумышленник мог бы принудить обе стороны использовать SSL 3.0 или слабый экспортный шифронабор. Защита обеспечивается сообщением `Finished`, которое содержит хеш всех Handshake-сообщений — любое изменение параметров переговоров делает Finished невалидным.

## Архитектура TLS-над-TCP

TLS встраивается между транспортным уровнем (TCP) и приложением, не меняя ни то, ни другое:

```
┌──────────────────────────────┐
│   Приложение (HTTP, SMTP…)   │  ← видит обычный поток байт
├──────────────────────────────┤
│       TLS Record Layer       │  ← шифрует, добавляет auth tag
│ ┌───────────┬──────────────┐ │
│ │ Handshake │ App Data     │ │
│ │ Alert     │ ChangeCipher │ │
│ └───────────┴──────────────┘ │
├──────────────────────────────┤
│       TCP (поток байт)       │  ← надёжная доставка
├──────────────────────────────┤
│             IP               │
└──────────────────────────────┘
```

Несколько практических следствий этой архитектуры:

- TLS требует уже **установленного** TCP-соединения. Сначала происходит TCP 3-way handshake, потом — TLS Handshake. До начала передачи данных суммарно тратится минимум 3 round-trip (TCP SYN + TLS).
- TLS не занимается повторной передачей пакетов — это задача TCP. TLS лишь добавляет шифрование и аутентификацию поверх надёжного потока.
- Для приложения TLS выглядит как обычный сокет: `write(data)` → `read(data)`. Шифрование прозрачно.
- Стандартные порты: **443** (HTTPS), 465 (SMTPS), 993 (IMAPS), 8443 (альтернативный HTTPS).
- `DTLS` — аналог для UDP, добавляет нумерацию и повторную передачу самостоятельно.

## Версии TLS и совместимость

| Версия | Байты в record | RFC | Статус |
|---|---|---|---|
| SSL 2.0 | — | — | Запрещён |
| SSL 3.0 | `03 00` | RFC 6101 | Запрещён (RFC 7568, 2015) |
| TLS 1.0 | `03 01` | RFC 2246 | Устарел (RFC 8996, 2021) |
| TLS 1.1 | `03 02` | RFC 4346 | Устарел (RFC 8996, 2021) |
| TLS 1.2 | `03 03` | RFC 5246 | Актуален, широко используется |
| TLS 1.3 | `03 03`* | RFC 8446 | Современный стандарт (2018) |

*TLS 1.3 притворяется версией 1.2 в поле record-заголовка (`03 03`) для совместимости с промежуточными узлами, которые отбрасывают незнакомые версии. Реальная версия согласуется через расширение `supported_versions` в ClientHello.

**Ключевые отличия TLS 1.3 от 1.2:**

- Handshake занимает **1 round-trip** (вместо 2): клиент сразу посылает `key_share` в ClientHello.
- **Сертификат и Finished сервера зашифрованы** — наблюдатель не видит сертификат.
- Запрещены: RSA для обмена ключами, CBC-режим, RC4, SHA-1 в подписях, сжатие.
- Только 5 шифронаборов, все AEAD. Нельзя случайно выбрать небезопасный.
- Введён **0-RTT** для возобновления сессий (с оговорками по безопасности).
- Поддержка **ECH** — шифрование ClientHello для сокрытия SNI.

## Ключи и типы шифрования

В TLS используются оба вида шифрования, и каждый решает свою задачу.

**Асимметричная криптография** (RSA, ECDSA, ECDH) применяется **только в Handshake**:
- Решает проблему первого контакта: как двум незнакомым сторонам договориться о секрете через открытый канал.
- Медленно: типичная RSA-2048 операция — ~1–2 мс; ECDSA-256 быстрее (~0.1 мс), но всё равно на порядки медленнее AES.
- Секретный ключ **никогда не покидает** сервер. По сети передаются только открытые ключи.

**Симметричная криптография** (AES-GCM, ChaCha20-Poly1305) применяется **для шифрования трафика**:
- Работает с ключом, который обе стороны уже знают (договорились через ECDHE).
- Скорость: AES-NI даёт 10–40 Гбит/с на современном CPU.
- Ключ существует только на время сессии (при использовании эфемерных ключей ECDHE).

**Почему TLS использует оба:** асимметрика решает задачу распределения ключей (key establishment), но слишком медленна для потока данных. Симметрика идеальна по скорости, но не может установить общий секрет без предварительной договорённости. Комбинация: ECDHE договаривается о секрете → из него выводятся симметричные ключи → они шифруют весь трафик.

**ECDHE подробнее**: каждая сторона генерирует случайное число (секрет `a` у клиента, `b` у сервера), вычисляет публичную точку на кривой (`A = a·G` и `B = b·G`) и обменивается ею. Общий секрет: клиент вычисляет `a·B = a·b·G`, сервер — `b·A = b·a·G`. Результат одинаков. Подслушивающий знает `A` и `B`, но задача найти `a` зная `A = a·G` — это ECDLP (вычислительно неразрешимо).

## Записи TLS и заголовки

Всё в TLS передаётся через **записи (records)** — это единственный формат на уровне транспорта TLS. Каждая запись имеет заголовок фиксированного размера 5 байт:

```
Байт 0:     ContentType  (1 байт)
Байты 1–2:  Version      (2 байта)
Байты 3–4:  Length       (2 байта, big-endian)
Байты 5…:   Data         (до 16384 байт открытого текста)
```

**Пример разбора реального заголовка** `16 03 03 00 F5`:

| Байты | Значение | Смысл |
|---|---|---|
| `16` | 22 | ContentType = Handshake |
| `03 03` | TLS 1.2 | Version (в TLS 1.3 тоже `03 03`) |
| `00 F5` | 245 байт | Длина следующего блока данных |

**ContentType** определяет, как интерпретировать тело записи:

| Hex | Dec | Тип |
|---|---|---|
| `0x14` | 20 | ChangeCipherSpec |
| `0x15` | 21 | Alert |
| `0x16` | 22 | Handshake |
| `0x17` | 23 | Application Data |

**Ограничения длины:**
- Открытый текст (plaintext): максимум 2¹⁴ = **16 384 байт**.
- Зашифрованная запись (TLS 1.2): до 18 432 байт (16 384 + 1024 паддинг + 1024 MAC).
- Зашифрованная запись (TLS 1.3): до 16 640 байт (16 384 + 256 auth tag).

Если приложение хочет передать больше 16 КБ за раз, TLS автоматически разбивает данные на несколько записей. Одно Handshake-сообщение тоже может быть разбито на несколько записей — корректная реализация должна это поддерживать.

---

## Типы записей: Handshake, Alert, Application Data

**Handshake (0x16)** — самый сложный тип. Тело записи содержит одно или несколько Handshake-сообщений, каждое со своим 4-байтовым заголовком: тип (1 байт) + длина (3 байта).

Типы Handshake-сообщений:

| Код | Сообщение | Кто шлёт |
|---|---|---|
| 1 | ClientHello | Клиент |
| 2 | ServerHello | Сервер |
| 11 | Certificate | Сервер (или клиент) |
| 12 | ServerKeyExchange | Сервер |
| 13 | CertificateRequest | Сервер |
| 14 | ServerHelloDone | Сервер |
| 15 | CertificateVerify | Клиент |
| 16 | ClientKeyExchange | Клиент |
| 20 | Finished | Оба |

**Alert (0x15)** — два байта: уровень (1 = warning, 2 = fatal) + код ошибки. Примеры кодов: `0x28` (40) = handshake_failure, `0x2a` (42) = bad_certificate, `0x30` (48) = unsupported_certificate. После fatal-алерта соединение немедленно закрывается. В TLS 1.3 тип Alert скрыт внутри зашифрованной Application Data записи.

**Application Data (0x17)** — зашифрованные данные приложения. До установления соединения этот тип не используется. После Finished — всё, что пишет приложение, оборачивается в такие записи. В TLS 1.3 в Application Data оборачиваются и зашифрованные Handshake-сообщения: снаружи виден тип `0x17`, а реальный тип (`0x16`) скрыт внутри после расшифровки.

## Логика TLS и Handshake TLS 1.2

Типичный полный Handshake в TLS 1.2 с ECDHE:

**1. ClientHello** (клиент → сервер, открытый текст)
- `client_version`: максимальная версия TLS, которую поддерживает клиент
- `client_random`: 32 случайных байта (используются при выводе ключей)
- `session_id`: если клиент хочет возобновить сессию — ID предыдущей; иначе пусто
- `cipher_suites`: список поддерживаемых шифронаборов в порядке предпочтения
- `compression_methods`: обычно только `null` (0x00)
- Extensions: SNI (имя хоста), `supported_groups` (список кривых), `signature_algorithms`, ALPN и др.

**2. ServerHello** (сервер → клиент, открытый текст)
- Выбранная версия (≤ максимальной из ClientHello)
- `server_random`: 32 случайных байта сервера
- Выбранный шифронабор (один из предложенных клиентом)
- Выбранный метод сжатия (обычно `null`)

**3. Certificate** (сервер → клиент)
- Цепочка сертификатов: сначала сертификат сервера, затем промежуточные CA
- Клиент проверяет подпись каждого сертификата в цепочке

**4. ServerKeyExchange** (сервер → клиент, только при ECDHE/DHE)
- Параметры кривой (идентификатор) и публичный ключ сервера `B = b·G`
- Подпись: `sign(server_priv_key, client_random + server_random + ECDHE_params)`
- Клиент верифицирует подпись открытым ключом из сертификата — так он убеждается, что ECDHE-параметры не подменены

**5. ServerHelloDone** — пустое сообщение, сигнал «жду ответа»

**6. ClientKeyExchange** (клиент → сервер)
- Клиент генерирует эфемерный ECDHE-ключ, вычисляет `A = a·G`
- Отправляет серверу публичную точку `A`
- Обе стороны независимо вычисляют `shared_secret = a·B = b·A = a·b·G`

**7. ChangeCipherSpec** (клиент → сервер)
- Не Handshake-сообщение, отдельный тип записи
- Сигнал: «следующие записи буду шифровать»

**8. Finished** (клиент → сервер, уже зашифровано)
- `verify_data = PRF(master_secret, "client finished", Hash(all_handshake_messages))`
- Сервер проверяет: вычисляет то же самое и сравнивает
- Защищает от подмены любого предыдущего сообщения Handshake

**9. ChangeCipherSpec + Finished** (сервер → клиент)
- Аналогично, но с меткой `"server finished"` и хешем, включающим клиентский Finished

После обмена Finished — канал установлен, начинается передача Application Data.

**Сокращённый Handshake (resumption):** если клиент предоставил в ClientHello валидный `session_id` или Session Ticket, сервер может пропустить шаги 3–6. Стороны восстанавливают master secret и выводят новые сеансовые ключи без повторного обмена сертификатами и ECDHE. Экономия: ~1 RTT и дорогие асимметричные операции.

## Цепочка сертификатов и проверка

Когда браузер получает сертификат сервера, он выполняет цепочку проверок:

**1. Построение цепочки:** сервер присылает свой сертификат + промежуточные CA. Браузер ищет путь от сертификата сервера до Root CA из своего доверенного хранилища.

**2. Проверка подписи каждого звена:** подпись на сертификате сервера должна верифицироваться открытым ключом Intermediate CA; подпись на Intermediate CA — открытым ключом Root CA.

**3. Проверка срока действия:** `Not Before` ≤ текущее время ≤ `Not After` для каждого сертификата в цепочке.

**4. Проверка имени (hostname verification):** Subject Alternative Name (SAN) в сертификате сервера должен совпадать с запрошенным доменом. Поддерживаются wildcard: `*.example.com` соответствует `api.example.com`, но не `sub.api.example.com`.

**5. Проверка отзыва:** через OCSP или CRL. OCSP Stapling позволяет серверу заранее получить подписанный OCSP-ответ и передавать его клиенту в Handshake — это быстрее и приватнее (без отдельного запроса к CA).

**Распространённые ошибки при верификации:**

- `CERTIFICATE_VERIFY_FAILED` — не удалось построить цепочку до доверенного Root CA (самоподписанный сертификат, отсутствует промежуточный CA)
- `HOSTNAME_MISMATCH` — CN/SAN не совпадает с доменом
- `CERTIFICATE_EXPIRED` — сертификат просрочен
- `CERTIFICATE_REVOKED` — сертификат отозван (OCSP вернул статус revoked)

## Сокрытие метаинформации

Шифрование трафика — лишь часть задачи. Даже без расшифровки наблюдатель получает из TLS значительный объём информации.

**Что видно без расшифровки:**

- **IP-адреса** клиента и сервера — всегда видны
- **SNI** в ClientHello — до TLS 1.3/ECH передаётся открытым текстом; провайдер знает, к какому домену вы подключаетесь
- **Размеры записей** — по паттерну размеров можно угадать тип контента (видео, текст, API-запрос)
- **Временны́е паттерны** — по частоте и длительности сессий можно установить активность пользователя
- **Certificate** (в TLS 1.2) — передаётся до шифрования, раскрывает CN сервера

**Меры в TLS 1.3:**

- `EncryptedExtensions`, `Certificate`, `CertificateVerify` и `Finished` сервера зашифрованы
- Все записи снаружи выглядят как Application Data (`0x17`), реальный тип скрыт
- **ECH (Encrypted Client Hello)** — шифрует весь ClientHello, включая SNI. Публичный ключ сервера для ECH публикуется в DNS (запись HTTPS/SVCB). Пока не получил широкого распространения
- **Padding** — нулевые байты добавляются в конец TLS-записи для маскировки реальной длины

**Практическое следствие:** даже с TLS 1.3 DPI-системы могут уверенно детектировать TLS-соединение по структуре ClientHello (фиксированные поля, расширения, список кривых). «Fingerprint» ClientHello — устойчивый идентификатор конкретной реализации TLS (браузер, curl, openssl).

## AES структура

**AES (Advanced Encryption Standard)** — симметричный алгоритм блочного шифрования, принятый в качестве мирового стандарта защиты данных. Работает с блоками 128 бит (16 байт) и ключами 128, 192 или 256 бит. Производит Nr раундов преобразований: 10 для AES-128, 12 для AES-192, 14 для AES-256.

**State** — основная структура данных: матрица 4×4 байта (16 байт = 128 бит). Входной блок преобразуется в State столбец за столбцом:
State после загрузки блока:\
s₀₀ s₀₁ s₀₂ s₀₃\
s₁₀ s₁₁ s₁₂ s₁₃\
s₂₀ s₂₁ s₂₂ s₂₃\
s₃₀ s₃₁ s₃₂ s₃₃

Каждый столбец State называется **Word** (4 байта = 32 бита).

**S-box** — таблица нелинейной замены: каждому байту соответствует уникальный выходной байт (256→256), стойкая к линейному криптоанализу.

**Key expansion** генерирует из основного ключа **Nb×(Nr+1)** 128-битных раундовых ключей (Nb=4). Для AES-128: 44 слова (11 раундов × 4 слова). Каждый раундовый ключ уникален и зависит от основного ключа.

### Четыре раундовых функции

Каждый из раундов AES (кроме первого и последнего) состоит из четырёх последовательных преобразований:
1) SubBytes() — нелинейная замена каждого байта
2) ShiftRows() — циклический сдвиг по строкам
3) MixColumns() — умножение на фиксированную матрицу
4) AddRoundKey() — XOR с раундовым ключом

### **1. SubBytes**
`s_{r,c} = SBox[s_{r,c}]` — каждый байт заменяется через S-box.

### **2. ShiftRows** 
Циклические сдвиги строк **влево**:\
Строка 0: 0 байт (без сдвига)\
Строка 1: 1 байт влево\
Строка 2: 2 байта влево\
Строка 3: 3 байта влево

**До → После ShiftRows:**

| До ShiftRows      | После ShiftRows    | Сдвиг      |
|-------------------|--------------------|------------|
| `s00 s01 s02 s03` | `s00 s01 s02 s03`  | 0 байт     |
| `s10 s11 s12 s13` | `s11 s12 s13 s10`  | 1 байт     |
| `s20 s21 s22 s23` | `s22 s23 s20 s21`  | 2 байта    |
| `s30 s31 s32 s33` | `s33 s30 s31 s32`  | 3 байта    |

### **3. MixColumns**
[2 3 1 1]   [s'0c]   [s0c]\
[1 2 3 1] × [s'1c] = [s1c]\
[1 1 2 3]   [s'2c]   [s2c]\
[3 1 1 2]   [s'3c]   [s3c]

### **4. AddRoundKey**
`State ^= RoundKey` — XOR всего State с 128-битным ключом раунда (4 слова) [file:1].

## Псевдокод AES

**Полный алгоритм AES-128 (FIPS-197, до 5.2):**

```python
Cipher(input, key):
    CipherKeySchedule(key, w)              # Key Expansion → w
    State = LoadBlock(input)               # 128 бит → State 4×4
    AddRoundKey(State, w[0:4])             # Начальный ключевой шаг
    
    for round = 1 to 9:                    # 9 полных раундов
        SubBytes(State)
        ShiftRows(State) 
        MixColumns(State)
        AddRoundKey(State, w[round*4:(round+1)*4])
    
    # Финальный раунд 10 (без MixColumns)
    SubBytes(State)
    ShiftRows(State)
    AddRoundKey(State, w[40:44])
    
    output = StateToBlock(State)
    return output
```

**Структура:**
- **Раунд 0**: только AddRoundKey  
- **Раунды 1-9**: все 4 функции
- **Раунд 10**: SubBytes + ShiftRows + AddRoundKey

## Nonce и доп. данные для дешифровки

**Как строится nonce в TLS 1.2 (AES-GCM):**

```
nonce = implicit_part (4 байта из key_block) + explicit_part (8 байт из записи)
```

Явная часть (explicit nonce) передаётся в открытом виде перед шифртекстом и, как правило, равна sequence number записи. Итого: 96-битный nonce = 32-битный salt + 64-битный счётчик.

**В TLS 1.3** явного nonce нет. Он вычисляется как:
```
nonce = write_iv XOR (sequence_number в big-endian, дополненный нулями до длины write_iv)
```

**AAD (Additional Authenticated Data) в TLS 1.2:**
```
AAD = seq_num (8 байт) + content_type (1) + version (2) + plaintext_length (2)
```

**AAD в TLS 1.3:**
```
AAD = content_type (1) + legacy_version (2) + ciphertext_length (2)
  (seq_num уже включён в nonce через XOR)
```

**Для дешифровки каждой TLS 1.2 AES-GCM записи нужно иметь:**

| Компонент | Размер | Где взять |
|---|---|---|
| `client_write_key` или `server_write_key` | 16/32 байт | Из key_block |
| `client_write_IV` или `server_write_IV` | 4 байта | Из key_block |
| Явный nonce из записи | 8 байт | Из wire-формата (перед шифртекстом) |
| Шифртекст | N байт | Из записи |
| Auth tag | 16 байт | Последние 16 байт записи |
| AAD | 13 байт | Реконструируется из заголовка + seq_num |

При работе с Botan: перехватить ключи в `Connection_Cipher_State` после завершения Handshake, логировать в hex. Для дешифровки офлайн: `openssl enc -d -aes-128-gcm -K <key_hex> -iv <nonce_hex>` или Python `cryptography.hazmat`.

## TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256

Шифронабор `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` (код `0xC02F`) декомпозируется:

| Часть | Алгоритм | Роль |
|---|---|---|
| `ECDHE` | Elliptic Curve Diffie-Hellman Ephemeral | Обмен ключами; эфемерные ключи → forward secrecy |
| `RSA` | RSA подпись | Аутентификация сервера; подписывает ECDHE-параметры и сертификат |
| `AES_128_GCM` | AES-128 в режиме GCM | Симметричное AEAD-шифрование трафика |
| `SHA256` | SHA-256 | Хеш-функция для PRF/HMAC; используется в KDF и Finished |

**Важное уточнение:** RSA здесь — только для **подписи**, не для передачи ключей. Premaster secret вычисляется через ECDHE. Это означает, что даже если приватный RSA-ключ сервера утечёт, прошлые сессии останутся защищены (forward secrecy от ECDHE).

**Почему именно этот шифронабор используется в задании (TLS 1.2):**
- ECDHE обеспечивает forward secrecy
- RSA-сертификаты — самые распространённые
- AES-128-GCM — аппаратно ускорен, AEAD
- SHA-256 — современная хеш-функция

Аналог в TLS 1.3 — шифронабор `TLS_AES_128_GCM_SHA256` (код `0x1301`). RSA и ECDHE больше не указываются в имени — они вынесены в отдельные расширения.

## Атаки и модель угроз TLS

**MITM (Man-in-the-Middle):** атакующий встаёт между клиентом и сервером, перехватывает трафик и подменяет сертификат своим. Предотвращается корректной проверкой цепочки сертификатов. Если пользователь принял поддельный сертификат (clicked «продолжить») — TLS скомпрометирован. HSTS (HTTP Strict Transport Security) усиливает защиту: браузер не пустит на сайт по HTTP и не примет самоподписанный сертификат.

**Padding oracle атаки (CBC-режим):**

Класс атак, основанных на том, что сервер по-разному реагирует на сообщения с неверным паддингом: возвращает разные ошибки или отвечает с разным временем. Это позволяет расшифровать произвольный блок шифртекста, отправляя модифицированные записи и наблюдая за реакцией — без знания ключа.

- **BEAST (2011):** атака на TLS 1.0 CBC. В TLS 1.0 IV следующего блока = последний шифртекстовый блок предыдущей записи, что позволяет атакующему предсказывать IV. Позволяет расшифровывать секретные куки.
- **Lucky 13 (2013):** timing-атака на CBC+HMAC. Разное время обработки в зависимости от длины паддинга раскрывает информацию о нём.
- **POODLE (2014):** атака на SSL 3.0 CBC через downgrade. Заставляет сервер откатиться до SSL 3.0, где паддинг не аутентифицирован.

**Закрытие:** все три закрыты переходом на AEAD (GCM). В AEAD нет отдельного паддинга, аутентифицируется весь шифртекст целиком.

**FREAK (2015):** атака эксплуатировала историческое требование США об «экспортных» ограничениях на криптографию (≤512-битный RSA). Оказалось, серверы всё ещё поддерживали такие шифронаборы. Атакующий принуждал к downgrade на экспортный RSA-512, факторизовал его за несколько часов, и мог расшифровать сессию. Закрыто удалением экспортных шифронаборов.

**Logjam (2015):** атака на DHE с 512-битными параметрами. Для нескольких стандартных 512-битных групп был заранее выполнен Number Field Sieve (занимает недели), и атакующий в реальном времени мог вычислять дискретные логарифмы за секунды. Атака позволяла расшифровывать сессии при downgrade до DHE-512. Закрыто требованием DHE ≥ 2048 или переходом на ECDHE.

**Heartbleed (CVE-2014-0160):** не атака на протокол. Расширение Heartbeat в OpenSSL позволяло запросить «эхо» произвольного размера без проверки реальной длины. Сервер копировал в ответ N байт из своей памяти, которая могла содержать приватный ключ, пароли, сессионные куки. Закрыто обновлением OpenSSL и перевыпуском всех сертификатов.

**Современный статус:** TLS 1.3 с ECDHE + AEAD архитектурно закрывает большинство этих векторов. Оставшиеся угрозы — реализационные баги (как Heartbleed), компрометация CA, социальная инженерия.
