## Словарик

Краткий справочник терминов, которые появляются в заданиях и статье tls.dxdt.ru.

| Термин | Расшифровка | Смысл |
|---|---|---|
| **TLS** | Transport Layer Security | Протокол защищённого канала поверх TCP (HTTPS, VPN и т.д.). Обеспечивает конфиденциальность, целостность и аутентификацию. |
| **SSL** | Secure Sockets Layer | Предшественник TLS, исторические версии (SSL 2.0/3.0) считаются небезопасными, используются только терминологически. |
| **Record (запись)** | TLS Record | Базовая единица данных TLS: заголовок + полезная нагрузка, шифруется/аутентифицируется целиком. |
| **Handshake** | Рукопожатие | Набор сообщений для согласования версии TLS, шифронаборов, генерации ключей и проверки сертификатов перед передачей данных. |
| **Cipher suite** | Криптонабор | Согласованный набор алгоритмов безопасности, которые используются для защиты сетевого соединения в протоколах SSL/TLS: обмен ключами (ECDHE/RSA), аутентификация (RSA/ECDSA), шифр (AES/ChaCha20), режим (GCM/CBC/CCM), хеш (SHA-256 и т.д.). |
| **AEAD** | Authenticated Encryption with Associated Data | класс режимов симметричного шифрования, который обеспечивает не только конфиденциальность (шифрование), но и целостность/подлинность данных (пример — AES-GCM). |
| **AES** | Advanced Encryption Standard | симметричный блочный алгоритм шифрования, который используется во всем мире для защиты секретных данных; в TLS обычно используется в режимах CBC, GCM, CCM. |
| **GCM** | Galois/Counter Mode | Высокопроизводительный режим шифрования данных (часто с AES), обеспечивающий одновременно конфиденциальность и целостность (AEAD). |
| **Nonce (IV)** | Number used once | Уникальные, несекретные случайные или счетные значения, используемые в криптографии для обеспечения того, чтобы один и тот же ключ шифрования каждый раз давал разный шифротекст. Они предотвращают атаки повторного воспроизведения и утечку данных. |
| **MAC / Auth Tag** | Message Authentication Code | Код аутентификации, добавляемый к данным для проверки их целостности и подлинности отправителя. В AEAD (GCM) называется тегом аутентификации, обычно 16 байт для TLS AES‑GCM. |
| **ClientHello** | — | Начальное сообщение от клиента (браузера) серверу при установке защищенного соединения TLS/SSL (рукопожатие/handshake), содержит версии TLS, список шифронаборов, случайные значения, расширения (SNI, ALPN, и т.д.). |
| **ServerHello** | — | Ответное сообщение, в котором сервер выбирает параметры из предложенных клиентом: выбранная версия, шифронабор, случайные данные сервера, часть расширений; запускает дальнейший обмен ключами. |
| **Certificate** | Сертификат X.509 | Цифровое «удостоверение личности» сайта (или сервера), которое подтверждает, что он тот, за кого себя выдает, подписанное центром сертификации (CA). |
| **Root CA** | Root Certificate Authority | Корневой УЦ, которому доверяет ОС/браузер. Его открытый ключ хранится в доверенном хранилище, а корневые сертификаты самоподписаны. |
| **PKI** | Public Key Infrastructure | Инфраструктура открытых ключей: корневые и промежуточные CA, цепочки сертификатов, списки отзыва. |
| **RSA** | Rivest–Shamir–Adleman | Ассиметричный алгоритм; в TLS 1.2 может использоваться для подписи сертификатов и (в старых профилях) для шифрования premaster secret. |
| **DHE / ECDHE** | (Elliptic Curve) Diffie–Hellman Ephemeral | Протокол согласования общего секрета. В TLS применяются ephemeral‑ключи (обеспечивают прозащиту вперёд). ECDHE использует эллиптические кривые. |
| **Premaster secret** | — | Cлучайная строка байтов, генерируемая клиентом в TLS-рукопожатии для создания сеансовых ключей шифрования. |
| **Master secret** | — | 48‑байтовый основной секрет сеанса в TLS 1.2, получаемый из premaster secret и случайных чисел клиента/сервера через PRF. |
| **Session keys** | Сеансовые ключи | Симметричные ключи и MAC‑ключи (или AEAD‑ключи) для шифрования трафика в каждом направлении. |
| **Forward secrecy** | Прозащита вперёд | Свойство: даже если приватный ключ сервера когда‑то утечёт, прошлые сеансы с ECDHE/DHE останутся недешифруемыми. |
| **MITM** | Man‑in‑the‑Middle | Атака «человек посередине»: перехват и подмена трафика между клиентом и сервером. TLS её предотвращает при корректной проверке сертификатов. |
| **FREAK** | Factoring RSA Export Keys | Историческая атака, использовавшая слабые экспортные RSA‑ключи и даунгрейд шифронаборов. |
| **Post‑quantum** | Постквантовая криптография | Алгоритмы, стойкие к квантовым атакам (например, не завязаны только на факторизацию/логарифмы). В классическом TLS 1.2 ещё не стандартизованы. |

## Назначение TLS

TLS решает три основные задачи: конфиденциальность (шифрование трафика), целостность (обнаружение подмены) и аутентификацию сторон (сертификаты и подписи).  
В модели угроз TLS считается, что атакующий полностью контролирует сетевой канал: может перехватывать, задерживать, удалять, дублировать и изменять любые TCP‑пакеты. Поэтому протокол одновременно обеспечивает конфиденциальность (шифрование), целостность (MAC/AEAD) и аутентификацию (сертификаты и подписи).

---

## Общий обзор TLS 1.2

TLS 1.2 строит защищённый канал поверх уже установленного TCP‑соединения (например, `HTTPS` над `TCP/443`).  
Протокол делится на уровни: Handshake (установка параметров и ключей), ChangeCipherSpec/Alert и Record Layer (пересылка и шифрование данных).

---

## Цифровые сертификаты и PKI

Серверный цифровой сертификат — это X.509‑структура, в которой указаны доменное имя/идентификатор сервера, его открытый ключ и подпись CA, подтверждающая связь между именем и ключом.  
Браузер/клиент строит и проверяет цепочку сертификатов до доверенного Root CA (корневого УЦ), чей самоподписанный сертификат лежит в системном хранилище доверия.

Root CA — корневая точка доверия: его открытый ключ «зашит» в ОС/браузеры, а на его основе проверяются подписи промежуточных CA и конечных сертификатов.  
Проверка включает: валидность подписи, непросроченность, соответствие имени (SNI/Host) и отсутствие сертификата в CRL/OCSP (если проверка включена).

## Ключи и типы шифрования

Открытый ключ — часть пары ключей, которую можно свободно распространять и использовать для проверки подписи или шифрования данных для владельца.  
Закрытый ключ — секретная часть пары, хранится только у владельца и используется для подписания или расшифровки.

Ассиметричное шифрование (RSA, ECDH‑подписи) использует разные ключи для шифрования и расшифровки/подписания и проверки подписи.  
Симметричное шифрование (AES, ChaCha20) использует один и тот же секретный ключ для шифрования и расшифровки, поэтому ключ нельзя раскрывать никому, кроме участников канала.

RSA в TLS 1.2 применяется в основном для подписей сертификатов и (в устаревших профилях) для шифрования premaster secret, что не даёт прозащиты вперёд.  
ECDHE использует эллиптические кривые для Диффи‑Хеллмана: стороны обмениваются открытыми точками, вычисляют общий секрет, но приватные «скаляры» никогда не выходят наружу, что даёт forward secrecy.

## Логика TLS и Handshake

Типичный полный handshake в TLS 1.2 с ECDHE выглядит так (сильно упрощённо).

1. ClientHello. Список поддерживаемых версий, шифронаборов, расширений, случайное число клиента.
2. ServerHello. Выбор версии и шифронабора, случайное число сервера.
3. Certificate (сервер). Цепочка сертификатов до CA.
4. ServerKeyExchange. Параметры ECDHE (кривая, открытый ключ сервера) + подпись.
5. [Optional] CertificateRequest. Запрос клиентского сертификата.
6. ServerHelloDone.
7. [Optional] Certificate (клиент).
8. ClientKeyExchange. Открытый ключ клиента для ECDHE.
9. [Optional] CertificateVerify. Подпись над хешем хэндшейка (клиентом).
10. ChangeCipherSpec (клиент).
11. Finished (клиент, уже шифруется).
12. ChangeCipherSpec (сервер).
13. Finished (сервер).

ClientHello содержит: версию протокола, `client_random` (32 байта), список шифронаборов, список compression methods (обычно только `null`) и расширения (SNI, elliptic_curve, supported_groups и т.д.).  
ServerHello возвращает выбранную версию, `server_random`, один шифронабор, compression method и подмножество расширений.

Сокращённый handshake (resumption) может использовать session id или session ticket: если клиент и сервер договорились возобновить существующую сессию, пропускаются шаги с сертификатами и обменом ключами.  
В этом случае стороны восстанавливают `master secret` и снова выводят симметричные ключи, что экономит RTT и CPU.

## Записи TLS и заголовки

Каждая запись TLS начинается с заголовка фиксированной длины 5 байт.

- Byte 0: ContentType (тип содержимого: 22 — handshake, 23 — application data, 21 — alert и т.д.).
- Bytes 1‑2: Версия протокола (например, 0x03 0x03 для TLS 1.2).
- Bytes 3‑4: Длина полезной нагрузки TLSPlaintext.length/TLSCiphertext.length (до 2^14 = 16384 байт для данных, плюс накладные поля шифра).

Максимальная длина поля данных для одной записи ограничена 16 КБ полезной нагрузки плюс MAC/паддинг/тег, поэтому общая зашифрованная длина может быть чуть больше значения 16384 за счёт накладных байт в режимах CBC/GCM.  
Спецификация TLS 1.2 разрешает, в некоторых случаях, увеличивать записи для внутренних нужд (например, padding для маскировки длины), что выглядит необычно, но формально укладывается в ограничения протокола.

Код аутентификации (MAC / auth tag) может вычисляться:  
- как HMAC поверх шифра (CBC + HMAC‑SHA256 — классический MAC‑then‑Encrypt);  
- как AEAD‑тег (например AES‑GCM), когда шифрование и аутентификация совмещены, а тег идёт отдельно в конце записи.

Для современных конфигураций лучше AEAD‑режимы (GCM, CCM, ChaCha20‑Poly1305), потому что они защищают от целого класса атак на CBC+HMAC (BEAST, Lucky13 и др.).

## TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256

Шифронабор `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` декомпозируется так:

- `ECDHE`: обмен ключами Диффи‑Хеллмана на эллиптических кривых, эфемерные ключи, даёт forward secrecy.
- `RSA`: алгоритм подписи в сертификате/ServerKeyExchange; сервер доказывает владение приватным RSA‑ключом.
- `AES_128_GCM`: симметричный шифр AES с ключом 128 бит в режиме AEAD GCM, обеспечивает шифрование и тег аутентификации.
- `SHA256`: хеш‑функция PRF/ХMAC (для вычисления master secret, ключевого материала и Finished‑хеша).

На практике это означает: RSA используется *только* для подписей (не для шифрования premaster secret), а само шифрование трафика делается симметрично AES‑128‑GCM с хешированием SHA‑256 в KDF.

## Симметричные ключи, master secret и KDF

В TLS 1.2 используется один master secret и несколько симметричных ключей, различающихся по направлению и назначению.

Типичная схема (до AEAD):

- `client_write_MAC_key`
- `server_write_MAC_key`
- `client_write_key` (ключ шифрования от клиента к серверу)
- `server_write_key` (ключ шифрования от сервера к клиенту)
- (опционально) IV/nonce‑ключи

В AEAD‑режимах фактически получается по одному AEAD‑ключу и набору IV/nonce‑материала на каждое направление.

Master secret (48 байт) генерируется функцией PRF на основе premaster secret (результат ECDHE), `ClientHello.random` и `ServerHello.random`:

\[
master\_secret = PRF(premaster\_secret, "master secret", ClientHello.random \Vert ServerHello.random)[1]
\]

Затем из master secret выводится key block — последовательность байтов, которая делится на отдельные симметричные ключи и IV для клиента и сервера.

Хеш‑функция SHA‑256 используется внутри PRF и HMAC (в классическом режиме) для связывания случайностей и premaster secret и для контроля целостности Finished‑сообщений.

## AES и режим GCM

AES использует блоки длиной 128 бит; характерная длина ключа в безопасных конфигурациях сегодня — 128 или 256 бит (в нашем шифронаборе 128 бит).  
Перебор 128‑битного ключа требует \(2^{128}\) операций, что считается недостижимым при текущем уровне вычислительной техники.

Типы шифров (с точки зрения структуры):

- Поточные (stream ciphers) — шифруют поток бит/байт (ChaCha20).
- Блочные (block ciphers) — шифруют фиксированные блоки с режимами (AES + CBC/GCM/CCM).

В AES над 128‑битными блоками выполняются линейные и нелинейные преобразования, которые можно представить как операции над матрицами в поле GF(2^8): SubBytes, ShiftRows, MixColumns и AddRoundKey.  
Для ключа 128 бит AES выполняет 10 раундов трансформации (4 этапа на раунд, кроме последнего, где нет MixColumns).

В режиме GCM каждый блок шифруется в счётчике (CTR), а тег аутентификации вычисляется как полином от шифртекста и дополнительных данных в поле GF(2^128).  
Тег обычно 128 бит (16 байт) и добавляется к каждой записи после шифртекста.

## Nonce и доп. данные для дешифровки

Для AES‑GCM в TLS 1.2 используется 96‑битный nonce, который по сути собирается из фиксированной части (salt из key_block) и счётчика последовательного номера записи.  
Критично: при одном и том же ключе пары (key, nonce) не должны повторяться; счётчик не должен «закручиваться».

Для успешной дешифровки каждой записи AES‑GCM нужно сохранить:

- симметричный AEAD‑ключ (client_write/server_write key для нужного направления);
- nonce (или возможность его восстановить из salt + sequence number);
- сам шифртекст записи (ciphertext);
- тег аутентификации (auth tag, обычно 16 байт);
- дополнительные аутентифицированные данные (AAD): тип записи, версия, длина и sequence number, которые входят в вычисление тега.

При инъекции в `Connection_Cipher_State` в Botan имеет смысл логировать именно окончательный ключ (или его hex) и nonce/IV для каждой установившейся сессии, без вывода реального трафика.

## Атаки и модель угроз TLS

Классические атаки на TLS и близкие протоколы:

- MITM — подмена сертификатов, попытка выдать поддельный CA или самоподписанный сертификат без предупреждения пользователя.
- Oracle‑атаки (padding oracle, Lucky13) — использование различных ответов/таймингов сервера при неверном MAC/паддинге, особенно на CBC‑режимах.
- FREAK — даунгрейд до экспортных RSA‑ключей, которые можно факторизовать, и далее расшифровка трафика.

Современные профили TLS 1.2/1.3 с ECDHE + AEAD‑шифрами и жёсткой политикой шифронаборов в значительной степени закрывают эти векторы.

## Библиотека Botan: карта и хуки

Задача карты Botan — проследить путь данных от вызовов уровня WebSocket/приложения до конкретных реализаций шифров AES‑GCM.

Рекомендуемая логическая структура конспекта:

- **Уровень TLS API**: классы, отвечающие за сессию (поддержка версий, handshake, re‑handshake, alerts).
- **Record Layer**: код, где формируются записи, вызываются AEAD‑объекты, инкрементируется sequence number.
- **Cipher State**: `Connection_Cipher_State` и сопряжённые классы для ключевого материала и направлений (read/write).
- **Crypto Backend**: классы конкретных AEAD (AES_128_GCM), их фабрики и регистрация.

Для задания по инъекции удобно добавить логирование в конструктор или метод установки ключей в `Connection_Cipher_State`, сохранив ключ и nonce в удобном для последующей дешифровки формате (например, hex + JSON‑лог).

## Проверка сертификатов в коде

Функция `Callbacks::tls_verify_cert_chain` в коде прошлого семестра вызывается библиотекой Botan/другим TLS‑стеком на этапе проверки цепочки сертификатов сервера.  
Типичные причины предупреждений: самоподписанный сертификат без доверенного CA, несовпадение имени (CN/SAN vs запрошенный хост), устаревший алгоритм подписи или отсутствие полного набора промежуточных сертификатов.

Чтобы проверить и воспроизвести проблему, нужно запустить код к предыдущему семестру с расширенным логированием в `tls_verify_cert_chain` (печать причин отказа/варнинга и деталей сертификата) и сверить с выводом `openssl s_client`/браузера.

## Полезные команды и утилиты

Примеры команд для исследования TLS‑параметров:

- `nmap --script ssl-enum-ciphers -p 443 fstream.binance.com` — посмотреть список версий TLS и шифронаборов, которые реально поддерживает сервер Binance.
- `openssl s_client -connect example.com:443 -servername example.com -tls1_2` — посмотреть сертификат, цепочку и детали шифронабора (включая ECDHE и AES‑GCM).
- `openssl x509 -in cert.pem -text -noout` — разобрать сертификат в человекочитаемом виде.

Эти утилиты хорошо дополняют «теорию» из tls.dxdt.ru и позволяют сверить поведение кода с тем, что происходит на уровне протокола.
